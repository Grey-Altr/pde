# Phase 136.1: Extensions Path Fix & Token Event Source — Research

**Researched:** 2026-03-25
**Domain:** Bug fix — wire envelope field path mismatch + PDE token event emission
**Confidence:** HIGH (all findings based on direct codebase inspection and confirmed transcript JSONL format)

---

## Summary

Phase 136.1 closes two bugs discovered during the v0.17 milestone audit. Both bugs are caused by assumptions made during implementation that don't match the actual data shape:

**Bug 1 — Extensions path mismatch (affects DSH-03, DSH-04, MON-01):** Three consumers read `extensions?.phase_name` and `extensions?.plan_name` from wire envelopes. But PDE events emit `phase_name` and `plan_name` as top-level payload fields, not inside an `extensions` sub-object. The relay wraps PDE events using `createEnvelope()` which spreads the PDE event into the wire envelope via `...pdeEvent` — so top-level fields stay top-level. The `extensions` sub-object is always present but always empty `{}`. Result: all three consumers see `undefined` and fall back to empty strings. Phase names and plan names never display.

**Bug 2 — Missing token event source (affects MON-02):** `deriveCost()` reads `input_tokens` and `output_tokens` as top-level wire envelope fields. No PDE event type currently emits these fields. The SubagentStop hook payload does not include token usage data. Token usage IS available by reading the `agent_transcript_path` from the SubagentStop hook payload — each JSONL line of type `assistant` contains `message.usage.input_tokens` and `message.usage.output_tokens`. PDE must emit a new `token_usage` event type by reading the transcript at SubagentStop time and summing per-subagent tokens.

**Primary recommendation:** Fix #1 is a ~10-line change across 3 files (read from top-level envelope). Fix #2 requires adding transcript-reading logic to `emit-event.cjs` for SubagentStop, emitting a `token_usage` event with summed `input_tokens` and `output_tokens` fields. `deriveCost` already reads from the correct top-level path — no change needed there.

### Pattern 1: Wire Envelope Top-Level Field Access

**What:** PDE events are spread into the wire envelope via `...pdeEvent`. All PDE payload fields (including `phase_name`, `plan_name`, `input_tokens`, `output_tokens`) appear at the top level of the `WireEnvelope` object, NOT inside `extensions`.

**Root cause of the bug:** The `WireEnvelopeSchema` defines `extensions` as an optional field, and the `event-bus.cjs` dispatch always includes `extensions: (payload && payload.extensions) || {}`. This means `extensions` is always present as an empty object. Consumers mistakenly read `ev.extensions?.phase_name` instead of `ev.phase_name`.

**How PDE events flow to wire envelopes:**
```
1. execute-phase.md calls:
   pde-tools.cjs event-emit phase_started '{"phase_number":"136.1","phase_name":"..."}'

2. pde-tools.cjs event-emit builds envelope:
   { schema_version, ts, event_type, session_id,
     phase_number: "136.1",       ← TOP-LEVEL
     phase_name: "...",           ← TOP-LEVEL
     extensions: {}               ← ALWAYS EMPTY
   }

3. relay-protocol.cjs createEnvelope spreads pdeEvent:
   { seq, session_id, machine_id, relay_ts, approval_id,
     ...pdeEvent                  ← phase_name STAYS TOP-LEVEL
   }

4. WireEnvelopeSchema.passthrough() accepts extra top-level fields
```

**The fix — read from top level:**
```typescript
// Source: direct codebase inspection of event-bus.cjs dispatch() and relay-protocol.cjs createEnvelope()

// BEFORE (wrong — extensions is always empty):
const ext = ev.extensions as Record<string, string> | undefined;
const phaseName = ext?.phase_name ?? '';

// AFTER (correct — top-level field):
const phaseName = (ev as Record<string, unknown>).phase_name as string ?? '';
```

### Pattern 2: SubagentStop Transcript Token Parsing

**What:** Claude Code's SubagentStop hook provides `agent_transcript_path` — a path to a JSONL file containing all assistant turns for that subagent. Each `type: "assistant"` line has `message.usage.input_tokens` and `message.usage.output_tokens`. Sum these for per-subagent token totals.

**Confirmed by:** Direct inspection of real transcript JSONL files at `~/.claude/projects/*/subagents/*.jsonl`.

**Transcript JSONL format (verified):**
```json
// type=assistant line — confirmed in real transcripts
{
  "type": "assistant",
  "message": {
    "usage": {
      "input_tokens": 3,
      "cache_creation_input_tokens": 1382,
      "cache_read_input_tokens": 10797,
      "output_tokens": 271
    }
  },
  "uuid": "...",
  "timestamp": "..."
}
```

**Token summation pattern:**
```javascript
// Source: direct transcript inspection (~/.claude/projects/*/subagents/*.jsonl)
// hooks/emit-event.cjs — SubagentStop handler addition

function sumTranscriptTokens(transcriptPath) {
  let inputTokens = 0;
  let outputTokens = 0;
  try {
    const lines = fs.readFileSync(transcriptPath, 'utf-8').trim().split('\n');
    for (const line of lines) {
      try {
        const obj = JSON.parse(line);
        if (obj.type === 'assistant' && obj.message?.usage) {
          inputTokens  += Number(obj.message.usage.input_tokens  ?? 0);
          outputTokens += Number(obj.message.usage.output_tokens ?? 0);
        }
      } catch { /* skip malformed line */ }
    }
  } catch { /* transcript missing or unreadable — swallow */ }
  return { inputTokens, outputTokens };
}
```

**Emitting the token_usage event:**
```javascript
// hooks/emit-event.cjs — in the SubagentStop branch
if (hookName === 'SubagentStop' && hookData.agent_transcript_path) {
  const { inputTokens, outputTokens } = sumTranscriptTokens(hookData.agent_transcript_path);
  const tokenPayload = {
    input_tokens:  inputTokens,
    output_tokens: outputTokens,
    agent_id:      hookData.agent_id,
  };
  // emit synchronously before main subagent_stop event
  spawnSync(process.execPath, [pdeTools, 'event-emit', 'token_usage', JSON.stringify(tokenPayload)], {
    encoding: 'utf-8',
    timeout: 5000,
  });
}
```

**Why emit before subagent_stop (not after):** Order doesn't matter for the relay (both events end up in the sorted set), but emitting token_usage first means the cost update reaches the dashboard before the subagent activity marker changes. Either order is acceptable.

### Pattern 3: WireEnvelope Type Assertion for Passthrough Fields

**What:** The `WireEnvelope` TypeScript type only includes the explicitly declared schema fields. Passthrough fields (like `phase_name`, `input_tokens`) are not in the type, so accessing them requires a cast.

**Pattern used by existing code (deriveCost already does this correctly):**

**Apply the same pattern for phase_name fixes:**

### Anti-Patterns to Avoid

- **Don't add `phase_name`/`plan_name` to `WireEnvelopeSchema`:** These fields are PDE-specific and not part of the RLY-02 required fields. The `.passthrough()` approach is correct — keep the schema minimal.
- **Don't move `phase_name` into `extensions`:** The PDE emit side already works. Only the read side is broken. Fix readers, not writers.
- **Don't change the `extensions` field behavior:** `event-bus.cjs` always initializes it to `{}`. This is intentional — consumers that look for structured data in `extensions` may exist. Leave `extensions` alone.
- **Don't use async file I/O in SubagentStop handler:** The emit-event.cjs pattern uses `spawnSync` throughout. Token transcript reading should use `fs.readFileSync` for consistency. The file is small enough (subagent transcript = hundreds of KB max) that sync read is fine.
- **Don't assume `agent_transcript_path` is always present:** Guard with `if (hookData.agent_transcript_path)` before reading. SubagentStop may fire without a transcript in edge cases.

## Common Pitfalls

### Pitfall 1: The `extensions` Object Trap

**What goes wrong:** Developer reads `ev.extensions?.phase_name` thinking PDE stores structured data under extensions. Returns `undefined` — falls through to `''` empty string. Phase names never appear.

**Why it happens:** The `WireEnvelopeSchema` defines `extensions: z.record(z.string(), z.unknown()).optional()` — looks like a container for extra fields. But `event-bus.cjs` dispatch always passes `extensions: {}` as a separate empty object while spreading PDE payload fields to the top level. The schema defines the shape, but the actual data flow puts PDE fields at the top.

**How to avoid:** Cast to `Record<string, unknown>` and read from the top level. The existing `deriveCost` implementation at lines 17-18 of `derive-cost.ts` shows the correct pattern.

**Warning signs:** Any code accessing `ev.extensions?.someField` where `someField` is a PDE event payload field — this is always wrong.

### Pitfall 2: Transcript Path Not Available

**What goes wrong:** SubagentStop hook fires but `agent_transcript_path` is absent or the file doesn't exist yet when the hook runs.

**Why it happens:** The transcript is written by Claude Code, not by PDE. There may be a brief race between Claude Code writing the final line and the hook reading the file. Also, `agent_transcript_path` may be absent for certain subagent types.

**How to avoid:** Wrap all transcript reads in a `try/catch`. If the file is missing or empty, emit `token_usage` with `{ input_tokens: 0, output_tokens: 0 }` — zero is a valid value for `deriveCost` (it returns `$0.00` gracefully).

**Warning signs:** `fs.readFileSync` throwing ENOENT in the SubagentStop handler.

### Pitfall 3: Test Coverage Doesn't Catch the Field Path

**What goes wrong:** Existing tests for `deriveProgress` use mock envelopes with `extensions: { phase_name: '136' }`. These tests pass with the old buggy code. After the fix, the tests need to use top-level `phase_name` on the envelope — both old and new test shapes need to be present.

**Why it happens:** The unit tests were written to match the original (incorrect) code path. The fix must also update the tests.

**How to avoid:** Update test fixtures to use top-level `phase_name`:
```typescript
// OLD (was testing the wrong thing):
mockEnvelope({ event_type: 'session_start', extensions: { phase_name: '136' } })

// NEW (tests the correct top-level path):
mockEnvelope({ event_type: 'session_start', phase_name: '136' })
```

Add new integration tests verifying the field path end-to-end (ingest route stores non-empty phase in Redis when event has top-level phase_name).

### Pitfall 4: plan_name Source vs. phase_name Source

**What goes wrong:** `phase_name` appears in `phase_started` events (emitted by execute-phase.md). But `plan_name` is not emitted — `plan_started` only emits `plan_id` (e.g., `"136.1-01"`).

**Why it matters:** After the extensions fix, `phase_name` will work. But `plan_name` will still be empty unless either (a) `plan_started` is updated to include a `plan_name` field, or (b) the dashboard parses `plan_id` to derive the plan name.

**How to avoid:** Two options:
1. Update `execute-plan.md` to emit `plan_name` as part of `plan_started` payload — requires workflow change.
2. Derive plan name from `plan_id` field that IS already emitted (e.g., display "Plan 01" derived from `plan_id: "136.1-01"`).

**Recommendation:** Option 2 first (derive from `plan_id`) for minimal blast radius. The phase description says "phase_name/plan_name from top-level wire envelope fields" — `plan_id` is also a top-level field that carries plan identity. Update `deriveProgress` to return `planName` derived from `plan_id` if `plan_name` is absent.

```typescript
// Source: dashboard/lib/derive-progress.ts (full file replacement)
import type { WireEnvelope } from '@/lib/wire-schema';

export interface PhaseProgressState {
  phaseName: string;
  planName: string;
}

export function deriveProgress(events: WireEnvelope[]): PhaseProgressState {
  // events are newest-first; find first event with a non-empty phase name
  for (const ev of events) {
    const payload = ev as Record<string, unknown>;   // access passthrough fields
    const phaseName = String(payload.phase_name ?? '');
    const planName  = String(payload.plan_name  ?? '') ||
                      String(payload.plan_id    ?? '');  // fallback: plan_id
    if (phaseName) return { phaseName, planName };
  }
  return { phaseName: '', planName: '' };
}
```

## Open Questions

1. **Should `plan_name` be added to the `plan_started` event emission in execute-plan.md?**
   - What we know: `plan_started` currently only emits `plan_id` (e.g., `"136.1-01"`). `plan_name` is not emitted anywhere.
   - What's unclear: Is the PLAN.md title available as a variable in the execute-plan.md context at emission time?
   - Recommendation: Use `plan_id` as the fallback display value for now (derive plan name as "Plan 01" from the `plan_id` field). Adding plan_name to the workflow emit is a separate enhancement that can be Phase 137+ work. The phase 136.1 success criteria say "phase_name/plan_name" — `plan_id` satisfies the spirit of plan identification.

2. **Double-counting tokens when agent runs multiple subagents?**
   - What we know: Each SubagentStop emits tokens for that subagent. `deriveCost` accumulates across all events.
   - What's unclear: Does the parent agent session have its own token usage that would be double-counted?
   - Recommendation: Parent agent token usage is in the MAIN session transcript (not subagent transcripts). The main session transcript is at `transcript_path` — but the SubagentStop hook fires per subagent. Parent turns are only in the main transcript. For now, only count subagent transcript tokens (SubagentStop handler). This is an approximation that errs toward under-counting, which is acceptable for v0.17.
