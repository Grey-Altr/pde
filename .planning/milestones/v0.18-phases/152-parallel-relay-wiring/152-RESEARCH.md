# Phase 152: Parallel Session Relay Wiring - Research

**Researched:** 2026-03-27
**Domain:** Node.js child_process management, NDJSON relay, Redis session state, CJS dependency injection
**Confidence:** HIGH

---

## Summary

Phase 152 closes the INT-RELAY gap: the DispatchCoordinator currently dispatches parallel sessions but never spawns relay.cjs child processes to forward those sessions' events to the dashboard via `/api/ingest`. DSP-08 was satisfied in Phase 144 by the in-process `Aggregator` (TailCursor-based), but RLY-01 specifically requires spawning `relay.cjs` as a separate child process per dispatched session.

There is a **critical session ID mismatch** that must be resolved first: the coordinator generates session IDs in the format `p144-1-abc12345` (8-char hex suffix), but `WireEnvelopeSchema.session_id` requires a valid UUID v4. Every envelope relay.cjs tries to send would fail schema validation and be silently dropped, meaning zero events would reach `/api/ingest`. Additionally, the NDJSON file written by executor sessions uses the UUID from `config.json monitoring.session_id` (generated by `session-start` at SessionStart hook), not the coordinator's session ID string. This means the aggregator's `watch()` and any relay.cjs spawned with the coordinator's string would both be polling the wrong path.

The fix requires two coordinated changes: (1) make `session-start` in `pde-tools.cjs` honor `PDE_SESSION_ID` when set (use it instead of generating a fresh UUID), and (2) add `_spawnRelay` to the coordinator's `_runSession` that spawns `relay.cjs` with the session's UUID, the ingest URL (from env `PDE_REMOTE`), and the relay token (from env `PDE_RELAY_TOKEN`). RLY-02 then follows automatically because `/api/sessions` already queries Redis via `getSessions()` and `deriveStatus()` — it just needs real data flowing in.

**Primary recommendation:** Add `_spawnRelay` to coordinator.cjs, fix `session-start` to honor `PDE_SESSION_ID`, and wire both together in `_runSession`. Follow the project's established `opts._deps` DI pattern throughout.

- **Zero-impact relay failures:** Relay errors must never surface to PDE or crash the coordinator. All relay-related code wraps in try/catch.
- **Source inspection tests** are acceptable for verifying structural properties without mocking complexities.

### Pattern 1: Pre-Assigned UUID for Relay Correlation

**What:** Coordinator generates a UUID *before* spawning the claude session, sets `PDE_SESSION_ID` to that UUID in the child environment. The `session-start` command in `pde-tools.cjs` is modified to use `PDE_SESSION_ID` when set, writing it to the worktree's `config.json monitoring.session_id` instead of generating a new one. This ensures the NDJSON file at `/tmp/pde-session-{UUID}.ndjson` is the one relay.cjs also watches.

**When to use:** Always, for all parallel sessions dispatched by coordinator.

**Example:**
```javascript
// coordinator.cjs — before spawning claude
const relaySessionId = crypto.randomUUID(); // a proper UUID v4

// In spawn.cjs, env already has:
env.PDE_SESSION_ID = relaySessionId; // pass UUID, not "p144-1-abc12345"

// In pde-tools.cjs session-start:
case 'session-start': {
  const { randomUUID } = require('crypto');
  // Honor PDE_SESSION_ID when set (parallel session mode)
  const newSessionId = process.env.PDE_SESSION_ID || randomUUID();
  // ... rest unchanged
}
```

### Pattern 2: Relay Child Process Spawn (mirrors start-relay.cjs)

**What:** Coordinator spawns `relay.cjs` as a detached child process with `unref()`, passing `[relaySessionId, ingestUrl, bearerToken]` as argv. A `_relays` Map tracks `{ pid, kill }` per session. On session end, the relay is killed and the Map entry removed.

**When to use:** In `_runSession` (local sessions only). Remote sessions already have their own relay via `spawnRemoteSession`.

**Example:**
```javascript
// coordinator.cjs _spawnRelay method
_spawnRelay(relaySessionId) {
  const ingestUrl   = process.env.PDE_REMOTE || '';
  const bearerToken = process.env.PDE_RELAY_TOKEN || '';
  if (!ingestUrl) return null; // no dashboard configured — skip silently

  const relayScript = require('node:path').join(
    require('node:path').dirname(require.resolve('../../../bin/lib/relay.cjs')),
    'relay.cjs'
  );

  try {
    const child = this._spawnChildProcess(
      process.execPath,
      [relayScript, relaySessionId, ingestUrl, bearerToken],
      {
        detached: true,
        stdio: ['ignore', 'ignore', 'ignore'],
        env: { ...process.env },
      }
    );
    child.unref();
    return { pid: child.pid, kill: (sig = 'SIGTERM') => { try { child.kill(sig); } catch (_) {} } };
  } catch (_) {
    return null; // relay spawn failure — never surfaces to PDE
  }
}
```

### Pattern 4: Relay Lifecycle Tied to Session Lifecycle

**What:** The coordinator tracks `_relays` Map (`sessionId → { pid, kill }`). Relay is spawned after `_aggregator.watch(sessionId)` (so both the aggregator and relay are watching the same file). Relay is killed in `_handleExit` after `_aggregator.unwatch(sessionId)`. `shutdown()` kills all relays.

**When to use:** Every `_runSession` call.

**Example:**
```javascript
// coordinator.cjs _runSession
_runSession(sessionId, phase, plan, worktreePath, branch) {
  return new Promise((resolve) => {
    // ... existing spawn setup ...

    // Spawn relay after aggregator watch (both watch /tmp/pde-session-{sessionId}.ndjson)
    const relayHandle = this._spawnRelay(sessionId);
    if (relayHandle) this._relays.set(sessionId, relayHandle);

    // ... rest unchanged ...
  });
}

// coordinator.cjs _handleExit (add relay cleanup)
async _handleExit(sessionId, exitCode, worktreePath, branch) {
  this._aggregator.unwatch(sessionId);
  this._sessions.delete(sessionId);

  // Kill relay process for this session
  const relayHandle = this._relays.get(sessionId);
  if (relayHandle) {
    relayHandle.kill();
    this._relays.delete(sessionId);
  }

  // ... rest unchanged ...
}

// coordinator.cjs shutdown
shutdown() {
  for (const { kill } of this._sessions.values()) kill();
  for (const { kill } of this._relays.values()) kill();  // add this
  this._aggregator.stopAll();
  this._tmuxFanout.stop();
}
```

### Anti-Patterns to Avoid

- **Using coordinator's `p144-1-abc12345` sessionId format as the relay session ID:** `WireEnvelopeSchema.session_id` requires a UUID. Verified: `z.string().uuid()` rejects non-UUID strings. Every envelope would be dropped silently.
- **Relying on `vi.mock('node:child_process')` for CJS tests:** CJS module binding caches references at require time. Use `vi.spyOn(childProcess, 'spawn')` OR `opts._deps.spawnChildProcess` injection. Established project decision from Phase 144.
- **Spawning relay before setting `PDE_SESSION_ID`:** The relay watches `/tmp/pde-session-{UUID}.ndjson`. The child session writes to `/tmp/pde-session-{monitoring.session_id}.ndjson`. These must be the same path, which requires `PDE_SESSION_ID` to be set to the UUID before `session-start` hook fires.
- **Blocking on relay spawn:** `child.unref()` is mandatory. The coordinator should not wait for relay to be ready before continuing session startup.
- **Surfacing relay errors to coordinator/PDE:** All relay spawn calls must be wrapped in try/catch. Relay failure is silent and non-blocking.
- **Spawning relay for remote sessions:** `_runRemoteSession` already has its own relay via the remote dispatch path. Only `_runSession` (local) needs coordinator-side relay.

## Common Pitfalls

### Pitfall 1: Session ID UUID Mismatch
**What goes wrong:** Coordinator spawns relay.cjs with `p144-1-abc12345` as session_id. Every envelope's `session_id` field fails `WireEnvelopeSchema.safeParse()` (verified: `z.string().uuid()` rejects it). Events are silently dropped. Dashboard shows nothing.
**Why it happens:** Coordinator generates sessionId as `p${phase}-${plan}-${crypto.randomUUID().slice(0, 8)}` — a readable ID, not a UUID.
**How to avoid:** Pre-assign a full UUID (`crypto.randomUUID()`) as `relaySessionId` before spawning, pass as `PDE_SESSION_ID` env var, modify `session-start` to use it when set.
**Warning signs:** `/api/ingest` returns 200 but Redis `pde:default:sessions` zset remains empty.

### Pitfall 2: NDJSON File Path Mismatch
**What goes wrong:** Relay watches `/tmp/pde-session-{coordSessionId}.ndjson` but executor session writes to `/tmp/pde-session-{UUID}.ndjson` (where UUID comes from `config.json monitoring.session_id`). Zero events ever reach relay.
**Why it happens:** `session-start` always generates a new UUID regardless of `PDE_SESSION_ID`. The UUID in config.json diverges from the coordinator's session ID.
**How to avoid:** Modify `session-start` to use `process.env.PDE_SESSION_ID` when set (single-line change: `const newSessionId = process.env.PDE_SESSION_ID || randomUUID()`).
**Warning signs:** Relay process is running (check `/tmp/pde-relay-{UUID}.pid`) but no events appear in Redis.

### Pitfall 3: Race Condition — Relay Starts Before NDJSON File Exists
**What goes wrong:** Relay spawns, immediately polls for `/tmp/pde-session-{UUID}.ndjson`, which doesn't exist yet. It returns silently. If TailCursor start-poll races before SessionStart hook fires, it misses the first few events.
**Why it happens:** `TailCursor._poll()` silently returns if `statSync` throws (file not found). This is intentional and correct — TailCursor handles file-not-yet-created gracefully by waiting for it to appear on the next poll interval.
**How to avoid:** No action needed. TailCursor already handles this correctly. The 500ms poll interval means at most 500ms of lost events at session start, which is acceptable.
**Warning signs:** First few events (`session_start`, early `subagent_start`) may not appear in dashboard. Not a bug — by design.

### Pitfall 4: Relay Process Leaking After Session End
**What goes wrong:** Session completes, `_handleExit` runs, but relay.cjs process keeps running (consuming CPU, polling dead NDJSON file, retrying failed HTTP requests).
**Why it happens:** `_relays` Map not cleaned up on session exit, or `shutdown()` doesn't kill relays.
**How to avoid:** Kill relay in `_handleExit` (after `_aggregator.unwatch`). Kill all relays in `shutdown()`. Follow the `_sessions` cleanup pattern exactly.
**Warning signs:** `ps aux | grep relay.cjs` shows orphaned processes after sessions complete.

### Pitfall 5: `PDE_REMOTE` Not Set — Relay Silently Skipped
**What goes wrong:** `_spawnRelay` checks `process.env.PDE_REMOTE`. If not set, returns null. `_relays` Map has no entry for this session. Session runs without dashboard monitoring. This is the CORRECT behavior (graceful degradation per CFG-05).
**Why it happens:** User hasn't configured dashboard URL.
**How to avoid:** This is intentional. `_spawnRelay` returning null is not an error. Document it clearly in the method.
**Warning signs:** None — this is expected behavior when dashboard is not configured.

### Pitfall 6: Remote Session Double-Relay
**What goes wrong:** `_runRemoteSession` path also calls `_spawnRelay`. Now two relays try to POST events for the same session.
**Why it happens:** Adding relay spawn to both local and remote paths.
**How to avoid:** Only call `_spawnRelay` in `_runSession` (local). `_runRemoteSession` already handles relay via SSH-side relay daemon.
**Warning signs:** Duplicate events in Redis sorted set; duplicate session entries.

## Open Questions

1. **Should coordinator relay UUID replace the `p144-1-abc12345` sessionId entirely, or be a separate field?**
   - What we know: The coordinator sessionId (`p144-1-abc12345`) is used for registry key, worktree path, branch name, NDJSON aggregator path. The relay UUID is used for dashboard/Redis. They are semantically different.
   - What's unclear: Whether making them the same (using UUID as coordinator sessionId) would simplify or complicate things.
   - Recommendation: Keep them separate. The coordinator sessionId has semantic meaning (phase/plan encoded). The relay UUID is dashboard-facing. Store relay UUID separately: either as a constructor arg to `_runSession` or as a second field in the registry entry. The simplest approach: `_runSession` calls `const relayId = crypto.randomUUID()` locally, uses it for both `PDE_SESSION_ID` env var and `_spawnRelay(relayId)`.

2. **Do aggregator.cjs watch paths need to be updated too?**
   - What we know: Aggregator watches `/tmp/pde-session-{coordinatorSessionId}.ndjson` but events go to `/tmp/pde-session-{UUID}.ndjson`. This is a pre-existing mismatch.
   - What's unclear: Whether aggregator (tmux/SSE consumers) needs to work in Phase 152 or is out of scope.
   - Recommendation: Phase 152 scope is relay → dashboard (RLY-01, RLY-02). Aggregator mismatch is a separate concern (tmux panes). Fix it if the same relayId solution is used — pass relayId to `this._aggregator.watch(relayId)` instead of coordinatorSessionId — but only if this doesn't break existing aggregator tests.
