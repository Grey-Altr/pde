    YAML frontmatter (following pde-research-validator.md pattern). The frontmatter block uses triple-dash delimiters and contains these fields:
    - name: pde-experiment-runner
    - description: Applies one atomic mutation per iteration, evaluates metric, returns structured result
    - argument-hint: "[experiment-md-path] [iteration] [baseline-sha] [context-mode full|diff]"
    - allowed-tools: Read, Edit, Bash
    - model: haiku

    Body sections (in order):

    **# pde-experiment-runner** -- One-line role: "You are PDE's experiment runner. You make ONE atomic change to the target file, evaluate the metric, and return a structured result."

    **## Your Constraints** -- Read-only with exceptions for Edit on mutable files only. List allowed tools and their scope. State: "You MUST NOT modify any file not listed in the mutable_files from experiment.md."

    **## Context Window** (SELF-06) -- Document the minimal context contract:
    - You receive ONLY: (1) experiment.md content, (2) target file content OR diff (based on context-mode argument), (3) last 3 results.jsonl rows, (4) metric output from previous iteration
    - You do NOT receive: full project context, codebase maps, prior phase summaries, or any file outside the experiment scope
    - This is by design -- minimal context = minimal token cost

    **## Iteration Protocol** -- Step-by-step instructions:
    1. Read experiment.md to understand metric, direction, verify command, mutable_files
    2. If context-mode is "full": Read each mutable file in full
    3. If context-mode is "diff": The diff of current-best vs baseline is provided in prompt (do NOT read full files -- use diff only)
    4. Analyze the search space described in experiment.md prose
    5. Make ONE atomic change using Edit tool on a mutable file
    6. Run boundary check: `node bin/pde-tools.cjs experiment check-boundaries --slug {slug}` -- if violations, undo Edit and try a different change (do NOT retry the same change)
    7. Run metric evaluation: `node bin/pde-tools.cjs experiment eval-metric --slug {slug}`
    8. Based on eval result, determine status: KEEP (metric improved per direction), DISCARD (metric regressed), CRASH (eval error)
    9. Write JSONL row: `node bin/pde-tools.cjs experiment write-row --slug {slug} --iteration {N} --metric_value {V} --metric_delta {D} --status {S} --description "{desc}" --tokens_used {T}`

    **## Model Escalation** (SELF-07) -- Document:
    - Default model is Haiku (set in frontmatter)
    - The orchestrating workflow (Phase 103) tracks consecutive_violations in EXPERIMENT-BEST.json
    - After 3 consecutive boundary violations or CRASH results, the orchestrator switches to Sonnet for subsequent iterations
    - On a successful KEEP, consecutive_violations resets to 0 but model stays escalated (no de-escalation)
    - The runner itself does NOT make the model selection decision -- it simply does its best with whichever model it is invoked as

    **## Diff-Based Context** (SELF-08) -- Document:
    - Iteration 1: context-mode=full, read complete target files
    - Iteration 2+: context-mode=diff, the orchestrator passes `git diff {baseline} HEAD -- {files}` output in the prompt
    - You work from the diff to understand current state, then propose your edit
    - If the diff is empty (first iteration or identical to baseline), read the full file

    **## Return Format** (EXEC-02) -- The runner returns a structured JSON block at the end of its response with these fields: iteration (number), metric_value (float), metric_delta (float), status ("KEEP"|"DISCARD"|"CRASH"), description (string), tokens_used (null -- populated by orchestrator).

    Note: tokens_used is set to null by the runner. The orchestrating workflow (Phase 103) populates it from Claude's API response after the agent returns.

    **## Boundary Enforcement** (EXEC-03) -- Document clearly:
    - Before any commit, you MUST verify modified files match mutable_files
    - If Edit modifies a file NOT in mutable_files, the boundary check will fail
    - On boundary violation: your change is discarded, no budget slot consumed, you retry with a different approach
    - You MUST NOT attempt to modify locked sections (marked `<!-- LOCKED -->`) even within mutable files
