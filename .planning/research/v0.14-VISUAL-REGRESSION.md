## 1. File-Hash Based Change Detection (Primary Strategy)

### How It Works

Node.js `crypto.createHash('sha256')` produces a deterministic 64-character hex digest for any file. For PNG screenshots, identical pixel data produces identical PNG bytes produces identical hash. Any visual change -- even a single pixel -- produces a completely different hash due to SHA-256's avalanche effect.

PDE already uses this exact pattern in `bin/lib/manifest.cjs`:

```javascript
// Existing pattern from manifest.cjs line 20-27
const crypto = require('crypto');
const fs = require('fs');

function hashFile(absolutePath) {
  try {
    const content = fs.readFileSync(absolutePath);
    return crypto.createHash('sha256').update(content).digest('hex');
  } catch {
    return null;
  }
}
```

### Binary Signal: Changed or Not

Hash comparison is a binary signal with zero false negatives for visual changes:

| Hash A === Hash B | Meaning |
|---|---|
| `true` | Screenshots are byte-identical -- no visual change occurred |
| `false` | Something changed -- could be 1 pixel or a complete redesign |

This is the correct primitive for a circuit breaker guard. The hash tells you THAT something changed. The metric score tells you WHETHER it was an improvement or regression.

### The Regression Detection Formula

```
visual_regression = hash_changed AND metric_decreased
```

Expanded:

```javascript
const crypto = require('crypto');
const fs = require('fs');

/**
 * Detect visual regression by combining hash change with metric direction.
 *
 * @param {string} baselinePath - Path to baseline screenshot PNG
 * @param {string} currentPath  - Path to current screenshot PNG
 * @param {number} baselineScore - Metric score at baseline
 * @param {number} currentScore  - Metric score for current iteration
 * @param {string} direction     - 'max' (higher=better) or 'min' (lower=better)
 * @returns {{ regression: boolean, hashChanged: boolean, scoreDelta: number, reason: string }}
 */
function detectVisualRegression(baselinePath, currentPath, baselineScore, currentScore, direction) {
  const baselineHash = hashScreenshot(baselinePath);
  const currentHash = hashScreenshot(currentPath);

  if (!baselineHash || !currentHash) {
    return { regression: false, hashChanged: false, scoreDelta: 0, reason: 'missing_screenshot' };
  }

  const hashChanged = baselineHash !== currentHash;
  const scoreDelta = currentScore - baselineScore;

  // No visual change at all -- no regression possible
  if (!hashChanged) {
    return { regression: false, hashChanged: false, scoreDelta, reason: 'no_visual_change' };
  }

  // Hash changed -- check metric direction
  const metricDecreased = direction === 'max'
    ? currentScore < baselineScore
    : currentScore > baselineScore;  // for 'min' direction, increase = worse

  if (metricDecreased) {
    return { regression: true, hashChanged: true, scoreDelta, reason: 'visual_change_with_score_decrease' };
  }

  return { regression: false, hashChanged: true, scoreDelta, reason: 'visual_change_with_score_improvement' };
}

function hashScreenshot(filePath) {
  try {
    const content = fs.readFileSync(filePath);
    return crypto.createHash('sha256').update(content).digest('hex');
  } catch {
    return null;
  }
}
```

### Limitations

1. **No granularity**: A 1-pixel anti-aliasing difference produces the same "changed" signal as a complete layout rearrangement. This is acceptable because the metric score provides the granularity -- the hash is only the "something changed" gate.

2. **PNG encoding determinism**: Playwright's `browser_take_screenshot` produces deterministic PNG output for identical page state. However, system font rendering differences across machines could produce different PNGs for the same HTML. This is not a concern for PDE because screenshots are compared within the same experiment run on the same machine.

3. **Metadata sensitivity**: PNG files can contain metadata (timestamps, software version). Playwright's output is consistent within a session, but if you wanted extra safety, hashing only the IDAT (pixel data) chunks would be more robust. For PDE's use case (same machine, same session), full-file hashing is sufficient.

### Confidence: HIGH

- `crypto.createHash('sha256')` is a Node.js built-in, zero dependencies
- Identical pattern already proven in `bin/lib/manifest.cjs`
- Binary change detection is mathematically sound (SHA-256 collision probability: ~2^-128)

## 2. File-Size Based Similarity Proxy

### How It Works

PNG compression is content-dependent. Visually simple regions (solid colors, gradients) compress well; complex regions (text, fine detail, noise) compress poorly. Changes in visual content change the compression ratio, which changes the file size.

```javascript
const fs = require('fs');

/**
 * Compare file sizes as a rough visual similarity proxy.
 *
 * @param {string} baselinePath - Path to baseline screenshot
 * @param {string} currentPath  - Path to current screenshot
 * @returns {{ sizeDelta: number, percentChange: number, significantChange: boolean }}
 */
function compareFileSize(baselinePath, currentPath) {
  const baselineSize = getFileSize(baselinePath);
  const currentSize = getFileSize(currentPath);

  if (baselineSize === null || currentSize === null) {
    return { sizeDelta: 0, percentChange: 0, significantChange: false };
  }

  const sizeDelta = currentSize - baselineSize;
  const percentChange = baselineSize > 0
    ? Math.abs(sizeDelta) / baselineSize * 100
    : 0;

  // 5% threshold: empirically, layout changes produce >5% size differences
  // while anti-aliasing noise stays under 1%
  const significantChange = percentChange > 5;

  return { sizeDelta, percentChange, significantChange };
}

function getFileSize(filePath) {
  try {
    return fs.statSync(filePath).size;
  } catch {
    return null;
  }
}
```

### Why File Size Correlates With Visual Changes

PNG uses DEFLATE compression on filtered scanlines. The correlation exists because:

| Visual Change | Effect on PNG Size |
|---|---|
| Adding elements (buttons, text, images) | Increases size (more entropy to encode) |
| Removing elements (simplifying layout) | Decreases size (less entropy) |
| Color changes (new palette) | Variable -- depends on compression of new patterns |
| Layout rearrangement (same elements, new positions) | Small change -- same entropy, different arrangement |
| Adding whitespace | Decreases size (solid regions compress well) |
| Adding fine detail/texture | Increases size significantly |

### Role in the Circuit Breaker: Supplementary Signal

File size is NOT a primary regression detector. It is a supplementary signal that adds context:

```javascript
/**
 * Enhanced regression detection with file-size context.
 */
function detectRegressionEnhanced(baselinePath, currentPath, baselineScore, currentScore, direction) {
  const hashResult = detectVisualRegression(baselinePath, currentPath, baselineScore, currentScore, direction);
  const sizeResult = compareFileSize(baselinePath, currentPath);

  return {
    ...hashResult,
    fileSizeDelta: sizeResult.sizeDelta,
    fileSizePercentChange: sizeResult.percentChange,
    significantSizeChange: sizeResult.significantChange,
    // Useful for logging: "visual regression detected, file size changed by +23%"
    // Helps humans understand the magnitude of the visual change
  };
}
```

### Limitations

1. **Not monotonic**: A "better" design does not reliably produce a larger or smaller file. Size change direction does not correlate with quality direction.

2. **Compression noise**: Identical visual output can have slightly different file sizes due to PNG filter selection heuristics. Typical noise is under 0.5%.

3. **Resolution dependence**: Size is meaningless without knowing the viewport dimensions. All comparisons must use the same viewport (enforced by Playwright's `browser_resize`).

### When to Use

- **Log it**: Always include file size delta in JSONL results for post-hoc analysis
- **Alert on large changes**: >20% size change alongside regression = likely major layout breakage
- **Do NOT use as primary signal**: Hash + metric score is the decision-maker

### Confidence: MEDIUM

- File size via `fs.statSync` is trivially available (zero dependencies)
- Correlation between visual complexity and PNG size is well-established in image processing literature
- The 5% threshold is a reasonable heuristic but may need calibration per experiment type

## 3. Structural DOM Comparison (No Images Needed)

### How It Works

Instead of comparing pixels, compare the DOM structure (element tree) or Playwright's accessibility tree (AOM snapshot). Structural comparison detects changes to what is in the page, not how it looks.

### Accessibility Tree as Structural Fingerprint

Playwright's `browser_snapshot` returns an accessibility tree (AOM) that PDE already plans to use for a11y critique (A11Y-01). This same tree can serve as a structural fingerprint:

```javascript
const crypto = require('crypto');

/**
 * Hash an accessibility tree snapshot for structural comparison.
 *
 * @param {string} snapshotText - Raw text from browser_snapshot
 * @returns {string} SHA-256 hash of the normalized snapshot
 */
function hashSnapshot(snapshotText) {
  // Normalize whitespace to reduce noise from formatting differences
  const normalized = snapshotText
    .split('\n')
    .map(line => line.trim())
    .filter(line => line.length > 0)
    .join('\n');

  return crypto.createHash('sha256').update(normalized).digest('hex');
}

/**
 * Count structural differences between two accessibility tree snapshots.
 *
 * @param {string} baselineSnapshot - AOM tree text before mutation
 * @param {string} currentSnapshot  - AOM tree text after mutation
 * @returns {{ added: number, removed: number, totalDelta: number, structuralChange: boolean }}
 */
function compareSnapshots(baselineSnapshot, currentSnapshot) {
  const baselineLines = parseSnapshotLines(baselineSnapshot);
  const currentLines = parseSnapshotLines(currentSnapshot);

  const baselineSet = new Set(baselineLines);
  const currentSet = new Set(currentLines);

  const added = currentLines.filter(l => !baselineSet.has(l)).length;
  const removed = baselineLines.filter(l => !currentSet.has(l)).length;

  return {
    added,
    removed,
    totalDelta: added + removed,
    structuralChange: added > 0 || removed > 0,
  };
}

function parseSnapshotLines(snapshot) {
  return snapshot
    .split('\n')
    .map(line => line.trim())
    .filter(line => line.length > 0);
}
```

### What Structural Comparison Detects

| Change Type | Screenshot Hash Detects | DOM/AOM Comparison Detects |
|---|---|---|
| Color change | Yes | No (structural identity unchanged) |
| Font change | Yes | No |
| Added heading | Yes | Yes (new heading node in tree) |
| Missing landmark | Yes | Yes (landmark removed from tree) |
| Reordered sections | Yes | Yes (line order changes) |
| Broken hierarchy | Yes | Yes (nesting depth changes) |
| CSS-only regression | Yes | No (DOM unchanged) |

### Structural Regression vs Improvement

For accessibility-focused experiments (AEXP-01, AEXP-02), structural changes have clear directional meaning:

```javascript
/**
 * Classify structural change direction for a11y experiments.
 *
 * @param {object} comparison - Output from compareSnapshots
 * @param {string[]} addedLines - Lines added in current snapshot
 * @returns {{ improvement: boolean, reason: string }}
 */
function classifyStructuralChange(baselineSnapshot, currentSnapshot) {
  const baselineMetrics = extractStructuralMetrics(baselineSnapshot);
  const currentMetrics = extractStructuralMetrics(currentSnapshot);

  const improvements = [];
  const regressions = [];

  // More landmarks = better a11y structure
  if (currentMetrics.landmarks > baselineMetrics.landmarks) improvements.push('added_landmarks');
  if (currentMetrics.landmarks < baselineMetrics.landmarks) regressions.push('lost_landmarks');

  // More ARIA labels = better
  if (currentMetrics.ariaLabels > baselineMetrics.ariaLabels) improvements.push('added_aria_labels');
  if (currentMetrics.ariaLabels < baselineMetrics.ariaLabels) regressions.push('lost_aria_labels');

  // Proper heading hierarchy = better
  if (currentMetrics.headingDepth > baselineMetrics.headingDepth) improvements.push('deeper_heading_hierarchy');

  return {
    improvements,
    regressions,
    netDirection: improvements.length > regressions.length ? 'improvement' : 'regression',
  };
}

function extractStructuralMetrics(snapshot) {
  const lines = snapshot.split('\n');
  return {
    landmarks: lines.filter(l => /\b(banner|navigation|main|contentinfo|complementary|region)\b/i.test(l)).length,
    ariaLabels: lines.filter(l => /aria-label/i.test(l)).length,
    headingDepth: Math.max(0, ...lines
      .filter(l => /\bheading\b/i.test(l))
      .map(l => {
        const match = l.match(/level[:\s]+(\d)/i);
        return match ? parseInt(match[1], 10) : 0;
      })),
    totalElements: lines.length,
  };
}
```

### Role in the Circuit Breaker

Structural comparison is a complementary signal to hash-based detection:

- **Hash changed + structure unchanged** = CSS-only change (color, spacing, font). Metric score alone determines regression.
- **Hash changed + structure changed** = Content change (elements added/removed). Both metric score and structural direction inform the decision.
- **Hash unchanged + structure unchanged** = No change at all. Skip evaluation.

### Confidence: HIGH

- All operations use string parsing and Set comparison -- zero dependencies
- Playwright's `browser_snapshot` output format is documented (line-oriented accessibility tree)
- Pattern is well-suited for a11y experiments specifically

## 4. Circuit Breaker Architecture

### Existing Circuit Breakers

PDE's experiment runner (from `workflows/optimize.md` step 7k) checks four circuit breakers in order:

| Breaker | Fires When | Config Field |
|---|---|---|
| BREAK-01: `iteration_budget` | `currentIteration >= iterationBudget` | `iteration_budget` in experiment.md (default 50) |
| BREAK-02: `time_budget` | `elapsedMinutes >= timeBudget` | `time_budget_minutes` in experiment.md (default 60) |
| BREAK-03: `consecutive_failures` | `consecutiveFailures >= limit` | `consecutive_failure_limit` in config.json (default 5) |
| BREAK-04: `no_progress` | `iterationsSinceImprovement >= limit` | `no_progress_limit` in config.json (default 10) |

All four operate on scalar values. The visual regression breaker adds a structural dimension.

### New: BREAK-05 `visual_regression_guard`

```
Fires when: screenshot hash changed AND metric score decreased from baseline
```

This is distinct from BREAK-04 (`no_progress`) because:
- `no_progress` fires after N iterations without improvement (stagnation)
- `visual_regression_guard` fires on a single iteration that is actively worse (regression)

### Integration Point in Experiment Loop

The visual regression check slots into step 7k of `optimize.md`, after metric evaluation but before the KEEP/DISCARD decision:

```
Step 7g: Run verify command → get metric_value
Step 7h: Compare metric to best (KEEP/DISCARD)
Step 7k: Check circuit breakers:
  1. BREAK-01: iteration_budget
  2. BREAK-02: time_budget
  3. BREAK-03: consecutive_failures
  4. BREAK-04: no_progress
  5. BREAK-05: visual_regression_guard  ← NEW
```

BREAK-05 fires AFTER the KEEP/DISCARD decision because it needs the metric comparison result.

### Implementation Contract

```javascript
const crypto = require('crypto');
const fs = require('fs');
const path = require('path');

/**
 * Check visual regression circuit breaker.
 *
 * Called after _evalMetric and _compareMetric in the experiment loop.
 *
 * @param {string} cwd - Working directory
 * @param {string} slug - Experiment slug
 * @param {string} currentScreenshotPath - Path to this iteration's screenshot
 * @param {number} currentScore - This iteration's metric value
 * @param {number} baselineScore - Baseline metric value (from EXPERIMENT-BEST.json)
 * @param {string} direction - 'max' or 'min'
 * @returns {{ fired: boolean, reason: string, baselineHash: string|null, currentHash: string|null }}
 */
function checkVisualRegressionBreaker(cwd, slug, currentScreenshotPath, currentScore, baselineScore, direction) {
  const baselinePath = path.join(cwd, '.planning', 'experiments', slug, 'baseline-screenshot.png');

  const baselineHash = hashFile(baselinePath);
  const currentHash = hashFile(currentScreenshotPath);

  // No baseline yet (first iteration) -- cannot detect regression
  if (!baselineHash) {
    return { fired: false, reason: 'no_baseline', baselineHash: null, currentHash };
  }

  // No current screenshot -- breaker cannot evaluate, skip
  if (!currentHash) {
    return { fired: false, reason: 'no_current_screenshot', baselineHash, currentHash: null };
  }

  // Hashes identical -- no visual change, no regression
  if (baselineHash === currentHash) {
    return { fired: false, reason: 'no_visual_change', baselineHash, currentHash };
  }

  // Hash changed -- check metric direction
  const metricDecreased = direction === 'max'
    ? currentScore < baselineScore
    : currentScore > baselineScore;

  if (metricDecreased) {
    return {
      fired: true,
      reason: 'visual_regression_detected',
      baselineHash,
      currentHash,
    };
  }

  return { fired: false, reason: 'visual_change_acceptable', baselineHash, currentHash };
}

function hashFile(filePath) {
  try {
    const content = fs.readFileSync(filePath);
    return crypto.createHash('sha256').update(content).digest('hex');
  } catch {
    return null;
  }
}
```

### Baseline Screenshot Lifecycle

```
.planning/experiments/{slug}/
  experiment.md              ← experiment definition
  results.jsonl              ← iteration log
  EXPERIMENT-BEST.json       ← best metric state
  baseline-screenshot.png    ← NEW: visual baseline (only updated on KEEP)
```

Lifecycle:

1. **First iteration**: No baseline exists. After eval, if KEEP, copy current screenshot to `baseline-screenshot.png`.
2. **Subsequent iterations**: Compare current screenshot hash against baseline hash.
3. **On KEEP**: Update baseline -- copy current screenshot to `baseline-screenshot.png` (the new "best-so-far").
4. **On DISCARD**: Do NOT update baseline. The baseline remains the best-known-good screenshot.
5. **On BREAK-05 fire**: Do NOT update baseline. Halt the loop.

```javascript
/**
 * Update baseline screenshot when a KEEP decision is made.
 *
 * @param {string} cwd - Working directory
 * @param {string} slug - Experiment slug
 * @param {string} currentScreenshotPath - Path to the screenshot that earned KEEP
 */
function updateBaselineScreenshot(cwd, slug, currentScreenshotPath) {
  const baselinePath = path.join(cwd, '.planning', 'experiments', slug, 'baseline-screenshot.png');
  try {
    fs.copyFileSync(currentScreenshotPath, baselinePath);
  } catch (err) {
    // Non-fatal: baseline update failure should not crash the experiment
    console.error(`Warning: could not update baseline screenshot: ${err.message}`);
  }
}
```

### Opt-In Configuration

Per VBRK-04, the visual regression guard is opt-in via experiment.md frontmatter:

```yaml
---
metric: visual-metric
direction: max
verify: node bin/visual-metric.cjs .planning/design/ux/wireframes/WFR-test.html
visual_regression_guard: true   # ← opt-in
mutable_files:
  - workflows/wireframe.md
---
```

Default is `false`. Text-only experiments (nyquist-metric) are unaffected.

### Confidence: HIGH

- Integrates cleanly into existing BREAK-01..04 pattern in optimize.md step 7k
- Uses same `hashFile` function proven in manifest.cjs
- EXPERIMENT-BEST.json already tracks baseline state; adding baseline-screenshot.png is a natural extension
- Opt-in via frontmatter uses existing `parseExperimentFile` parsing infrastructure

## 5. Before/After Delta Measurement (Iterate Experiments)

### The Problem

The iterate skill (iterate.md) takes a wireframe with known issues and produces an improved version. To measure whether iterate.md prose changes actually improve the iterate skill, we need a before/after delta metric.

### iterate-delta-metric Architecture

```
1. Start with reference wireframe (fixed, known-flawed input)
2. Screenshot the reference wireframe → pre-score via visual-metric
3. Run iterate with current iterate.md guidance → produces improved wireframe
4. Screenshot the improved wireframe → post-score via visual-metric
5. Delta = post-score - pre-score
6. Return delta as the metric value (direction: max → larger delta = better iterate guidance)
```

### Implementation

```javascript
#!/usr/bin/env node
'use strict';
/**
 * iterate-delta-metric.cjs
 *
 * Measures iterate effectiveness by computing before/after visual score delta.
 * Contract: exit 0, last line of stdout = numeric delta value.
 *
 * Usage: node bin/iterate-delta-metric.cjs <reference-wireframe-path> <iterated-wireframe-path>
 */

const { spawnSync } = require('child_process');
const path = require('path');

const referenceFile = process.argv[2];
const iteratedFile = process.argv[3];

if (!referenceFile || !iteratedFile) {
  // Degrade gracefully per VMET-07 contract
  process.stdout.write('0\n');
  process.exit(0);
}

// Score both wireframes using the same visual-metric
const preScore = runVisualMetric(referenceFile);
const postScore = runVisualMetric(iteratedFile);

const delta = postScore - preScore;
process.stdout.write(String(delta) + '\n');
process.exit(0);

function runVisualMetric(filePath) {
  const result = spawnSync('node', [path.join(__dirname, 'visual-metric.cjs'), filePath], {
    encoding: 'utf-8',
    stdio: 'pipe',
    timeout: 60000,
  });

  if (result.status !== 0) return 0;

  const lines = (result.stdout || '').split('\n').filter(Boolean);
  const lastLine = lines[lines.length - 1] || '0';
  const parsed = parseFloat(lastLine);
  return Number.isFinite(parsed) ? parsed : 0;
}
```

### Fixed Reference Wireframe Design

The reference wireframe must have known, measurable issues that iterate.md guidance should fix. This creates a consistent "before" state across experiment iterations:

**Known issues to embed in the reference wireframe:**

| Issue Category | Specific Flaw | How visual-metric Detects It |
|---|---|---|
| Poor hierarchy | No `<main>` landmark, flat heading structure (all `<h3>`) | Low landmark count, shallow heading depth |
| Missing landmarks | No `<nav>`, no `<footer>`, no `role="banner"` | Low landmark count in AOM tree |
| Weak contrast | Light gray text on white background (#aaa on #fff) | Low contrast ratio via contrast-metric |
| No interactive elements | Static text only, no buttons or links | Zero interactive element count |
| Poor whitespace | Content crammed edge-to-edge, no padding | Low whitespace ratio |
| Broken responsive | Fixed-width elements that overflow on mobile | responsive-metric detects overflow at 375px |

**Storage:** `references/experiments/reference-wireframe-flawed.html`

This file is immutable during experiments. It represents a "typical bad wireframe" that the iterate skill should be able to improve.

### Why a Fixed Input Matters

Without a fixed reference wireframe, the delta metric would depend on:
1. The quality of the brief (varies per project)
2. The randomness of LLM wireframe generation
3. The specific design concept

By fixing the input, the only variable is the iterate.md prose -- which is exactly what the experiment is optimizing.

### Confidence: HIGH

- Uses `spawnSync` (built-in) to call existing visual-metric.cjs
- Delta computation is trivial subtraction
- Fixed-input pattern is established in PIPE-05 (test-concept.md) and AEXP-03

## 6. Alternative Approaches: Evaluated and Rejected

### pixelmatch (npm package)

**What it does:** Pixel-by-pixel comparison of two images, returns count of differing pixels and generates a visual diff image.

**Why it is the best technical solution:** pixelmatch compares actual pixel data in decoded RGBA buffers, handles anti-aliasing tolerance, and produces a diff image showing exactly what changed. It is the standard approach for visual regression testing (used by Playwright's built-in screenshot comparison, Chromatic, Percy).

**Why rejected:** Requires `npm install pixelmatch pngjs`. PDE has a strict zero-npm-dependency constraint at the plugin root. Installing pixelmatch would also pull in pngjs for PNG decoding, creating a dependency chain.

### resemble.js (npm package)

**What it does:** Perceptual image comparison with tolerance for anti-aliasing, color shifts, and brightness changes. Returns a percentage difference score.

**Why rejected:** Same constraint -- npm dependency. Also heavier than pixelmatch (includes its own image processing pipeline).

### ImageMagick `compare` (system dependency)

**What it does:** Command-line image comparison producing diff images and numeric similarity scores.

```bash
compare -metric RMSE baseline.png current.png diff.png
```

**Why rejected:** Not guaranteed to be installed on user machines. PDE cannot assume system-level dependencies beyond Node.js. Would require:
- Detection of ImageMagick availability
- Graceful degradation when absent
- Different behavior across macOS (Homebrew), Linux (apt), Windows

The operational complexity is not justified when hash + metric score provides sufficient regression detection.

### Canvas-based comparison (npm: `canvas` or `sharp`)

**What it does:** Decode PNG into pixel buffer using native bindings, then compare pixel-by-pixel in JavaScript.

**Why rejected:** Both `canvas` (node-canvas) and `sharp` are npm packages with native compilation dependencies (libcairo, libvips). They are among the most fragile npm dependencies due to platform-specific binary compilation.

### Built-in `Buffer.compare` on raw PNG

**What it does:** Compare two PNG file buffers byte-by-byte.

**Why it is equivalent to hash comparison:** `Buffer.compare(a, b) === 0` is functionally identical to `hashFile(a) === hashFile(b)`. Both answer the same binary question: "are these files identical?" Hash comparison is preferred because:
- Hash can be stored cheaply (64 chars vs entire file)
- Hash can be logged in JSONL for post-hoc analysis
- Hash comparison pattern already exists in manifest.cjs

### Why File-Hash + Metric Score Is the Pragmatic Zero-Dep Solution

The key insight: PDE does not need to know HOW the screenshots differ. PDE needs to know:

1. **Did the screenshot change?** (hash comparison -- binary answer)
2. **Did the quality improve or regress?** (metric score -- numeric answer)

Full pixel-level comparison (pixelmatch, resemble.js, ImageMagick) provides information PDE cannot act on. The experiment loop makes KEEP/DISCARD decisions based on a single numeric metric. A per-pixel diff image or percentage-difference score does not change the KEEP/DISCARD decision -- only the metric score does.

The hash serves as a gate: if the hash is unchanged, we know the visual output is identical, so any metric score difference would be measurement noise (which should not happen with deterministic metrics, but is a useful sanity check).

```
                  Screenshot Hash
                  /            \
            Same Hash       Different Hash
               |                |
         No regression     Check metric score
                              /        \
                     Score better    Score worse
                         |              |
                    No regression   REGRESSION → fire breaker
```

This decision tree requires zero image processing libraries. It requires only:
- `crypto.createHash('sha256')` -- Node.js built-in
- `fs.readFileSync` / `fs.statSync` -- Node.js built-in
- The metric score (already computed by visual-metric.cjs via Playwright)

### Confidence: HIGH

- pixelmatch, resemble.js, canvas are definitively npm packages (verified)
- ImageMagick is definitively a system dependency (verified)
- The hash + metric approach provides equivalent decision quality for PDE's use case
- The zero-dependency constraint is a hard requirement from PROJECT.md ("zero npm dependencies")

## 7. Implementation Recommendations for Phase 115

### New Module: `bin/lib/visual-regression.cjs`

Single module exporting three functions, under 100 lines:

```javascript
'use strict';
/**
 * visual-regression.cjs — Visual regression detection for experiment circuit breaker.
 *
 * Zero npm dependencies. Uses Node.js built-in crypto + fs.
 *
 * Exports:
 *   hashScreenshot(filePath)                           -> string | null
 *   checkVisualRegression(opts)                        -> { fired, reason, ... }
 *   updateBaseline(cwd, slug, screenshotPath)          -> void
 */

const crypto = require('crypto');
const fs = require('fs');
const path = require('path');

function hashScreenshot(filePath) {
  try {
    const content = fs.readFileSync(filePath);
    return crypto.createHash('sha256').update(content).digest('hex');
  } catch {
    return null;
  }
}

function checkVisualRegression({ cwd, slug, currentScreenshotPath, currentScore, baselineScore, direction }) {
  const baselinePath = path.join(cwd, '.planning', 'experiments', slug, 'baseline-screenshot.png');
  const baselineHash = hashScreenshot(baselinePath);
  const currentHash = hashScreenshot(currentScreenshotPath);

  if (!baselineHash) return { fired: false, reason: 'no_baseline', baselineHash: null, currentHash };
  if (!currentHash) return { fired: false, reason: 'no_current_screenshot', baselineHash, currentHash: null };
  if (baselineHash === currentHash) return { fired: false, reason: 'no_visual_change', baselineHash, currentHash };

  const metricDecreased = direction === 'max'
    ? currentScore < baselineScore
    : currentScore > baselineScore;

  if (metricDecreased) {
    return { fired: true, reason: 'visual_regression_detected', baselineHash, currentHash };
  }

  return { fired: false, reason: 'visual_change_acceptable', baselineHash, currentHash };
}

function updateBaseline(cwd, slug, screenshotPath) {
  const baselinePath = path.join(cwd, '.planning', 'experiments', slug, 'baseline-screenshot.png');
  try {
    fs.copyFileSync(screenshotPath, baselinePath);
  } catch {
    // Non-fatal
  }
}

module.exports = { hashScreenshot, checkVisualRegression, updateBaseline };
```

## 8. Divergence Metric: File-Size Standard Deviation

For IDIV-01 (ideation visual divergence), file-size standard deviation serves as a proxy for visual distinctiveness among generated concepts:

```javascript
/**
 * Compute visual divergence from a set of screenshot file sizes.
 * Higher standard deviation = more visually diverse concepts.
 *
 * @param {string[]} screenshotPaths - Paths to concept screenshot PNGs
 * @returns {number} Standard deviation of file sizes (0 if < 2 files)
 */
function computeDivergence(screenshotPaths) {
  const sizes = screenshotPaths
    .map(p => { try { return fs.statSync(p).size; } catch { return null; } })
    .filter(s => s !== null);

  if (sizes.length < 2) return 0;

  const mean = sizes.reduce((a, b) => a + b, 0) / sizes.length;
  const variance = sizes.reduce((sum, s) => sum + Math.pow(s - mean, 2), 0) / sizes.length;
  return Math.sqrt(variance);
}
```

This is intentionally rough. Three concepts that all look the same will have similar file sizes (low stddev). Three concepts with different layouts, density, and element counts will have different file sizes (high stddev). The metric is adequate for detecting convergence vs divergence, which is the IDIV experiment's goal.
