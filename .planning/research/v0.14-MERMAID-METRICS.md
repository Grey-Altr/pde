## 1. Rendering Mermaid in a Browser Page

### 1.1 CDN Loading (Recommended)

**Confidence: HIGH** -- verified via official Mermaid docs and jsdelivr CDN

Mermaid v11 is the current major version (latest: 11.12.3). Use the ESM module from jsdelivr:

```html
<!DOCTYPE html>
<html>
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <title>Mermaid Metric Renderer</title>
  <style>
    body { margin: 0; padding: 16px; background: #fff; }
    #output { width: 100%; }
    .error { color: red; font-family: monospace; }
  </style>
</head>
<body>
  <div id="output"></div>
  <script type="module">
    import mermaid from 'https://cdn.jsdelivr.net/npm/mermaid@11/dist/mermaid.esm.min.mjs';

    // DIAGRAM_PLACEHOLDER will be replaced by mermaid-metric.cjs
    const definition = `MERMAID_DEFINITION_HERE`;

    mermaid.initialize({
      startOnLoad: false,
      securityLevel: 'loose',
      theme: 'default',
      flowchart: {
        useMaxWidth: false,
        htmlLabels: true,
        curve: 'basis'
      }
    });

    try {
      const { svg } = await mermaid.render('mermaid-diagram', definition);
      // Note: assigning render output to container is safe -- Mermaid sanitizes
      // via DOMPurify internally before returning the SVG string
      document.getElementById('output').insertAdjacentHTML('beforeend', svg);
      window.__MERMAID_RENDERED__ = true;
    } catch (err) {
      document.getElementById('output').textContent = 'Parse error: ' + err.message;
      window.__MERMAID_RENDERED__ = false;
      window.__MERMAID_ERROR__ = err.message;
    }
  </script>
</body>
</html>
```

### 1.2 API Methods

**Confidence: HIGH** -- official documentation

| Method | Purpose | Use in mermaid-metric.cjs |
|--------|---------|--------------------------|
| `mermaid.initialize(config)` | Configure before rendering | Set `startOnLoad: false`, theme, security |
| `mermaid.render(id, definition)` | Render string to SVG programmatically | **PRIMARY** -- render the definition string |
| `mermaid.parse(text)` | Validate syntax without rendering | Pre-validation before render attempt |
| `mermaid.run({querySelector})` | Process DOM elements with class="mermaid" | Alternative approach (less control) |

**Key distinction:** `mermaid.render()` returns `{ svg, bindFunctions }` and is the correct API for programmatic rendering from a string. `mermaid.run()` scans the DOM for `.mermaid` elements and replaces them in-place -- less suitable for metric extraction because you need the rendered SVG in a known container.

### 1.3 Waiting for Render Completion

**Confidence: HIGH**

The `mermaid.render()` call is `async` and returns a Promise. After `await`, the SVG string is ready. However, once injected into the DOM, the browser needs a frame to lay out the SVG. The recommended approach:

```javascript
// In the HTML template:
const { svg } = await mermaid.render('mermaid-diagram', definition);
document.getElementById('output').insertAdjacentHTML('beforeend', svg);
window.__MERMAID_RENDERED__ = true;
```

In `mermaid-metric.cjs`, use `browser_evaluate` to poll:

```javascript
// Via browser_evaluate after navigating to the HTML page:
return window.__MERMAID_RENDERED__ === true;
```

Or use `browser_wait_for` to wait for the SVG element to appear:

```javascript
// Wait for the rendered SVG to exist in the DOM
browser_wait_for({ selector: '#output svg', timeout: 10000 });
```

### 1.4 Minimal HTML Wrapper Strategy for mermaid-metric.cjs

The script should:

1. Read the Mermaid definition from the input file (parse markdown, extract fenced `mermaid` code blocks)
2. Generate a temporary HTML file with the definition embedded
3. Serve it via `npx serve` on a random port (file:// URLs are blocked by Playwright MCP by default -- see PLAYWRIGHT-MCP-DEEP.md)
4. Navigate Playwright to the served URL
5. Wait for `window.__MERMAID_RENDERED__` to be true
6. Run `browser_evaluate` to extract metrics from the rendered SVG DOM
7. Compute score, print to stdout, exit 0

**Alternative if file:// is available (PLAY-05 resolved):** Skip the serve step and navigate directly to `file:///tmp/mermaid-metric-{hash}.html`. This is simpler but depends on Phase 108 resolution.

### 2.2 Stable CSS Selectors for Metric Extraction

**Confidence: MEDIUM** -- verified from Cypress test files and multiple community sources. The `.node` and `.edgePath` classes have been stable since at least Mermaid v9.

| Element | Selector | What It Returns |
|---------|----------|-----------------|
| All nodes | `svg .node` | `<g>` elements for each node |
| All edge paths | `svg .edgePath` | `<g>` elements containing `<path>` |
| Edge path lines | `svg .edgePath path` or `svg .flowchart-link` | The actual `<path>` elements |
| Edge labels | `svg .edgeLabel` | Label containers |

### 2.4 CSS Class Stability Warning

**Confidence: MEDIUM**

Mermaid v11 source shows class names are assigned in rendering functions (`insertNode`, `insertEdge`, `insertCluster`). The `.node`, `.edgePath`, `.edgeLabel`, `.cluster` top-level group classes have been stable across v9-v11. However:

- The **case** of class names in the actual DOM may differ from the source (`edgePath` vs `edgepath`) -- one source reports lowercase conversion in the DOM. The metric script should use case-insensitive matching or test both variants.
- Inner element classes (`.basic`, `.label-container`, `.flowchart-link`) are more likely to change between minor versions.
- Node IDs follow the pattern `flowchart-{nodeId}-{counter}` but the counter is non-deterministic.

### 3.2 Edge Count and Edge Crossing Detection

**Confidence: MEDIUM** -- bounding box heuristic is practical; true geometric intersection is complex

Edge crossing is the hardest metric to compute. True path intersection requires geometric analysis. A practical heuristic using bounding box overlap:

```javascript
// browser_evaluate script -- edge crossing heuristic
(() => {
  const svg = document.querySelector('#output svg');
  if (!svg) return { error: 'No SVG found' };

  // Get all edge path elements
  const edgePaths = svg.querySelectorAll('.edgePath path, .flowchart-link');
  const edgeCount = edgePaths.length;

  // Bounding box overlap heuristic for crossings
  const boxes = Array.from(edgePaths).map(p => {
    const rect = p.getBoundingClientRect();
    return { left: rect.left, right: rect.right, top: rect.top, bottom: rect.bottom };
  });

  let crossings = 0;
  for (let i = 0; i < boxes.length; i++) {
    for (let j = i + 1; j < boxes.length; j++) {
      const a = boxes[i];
      const b = boxes[j];
      // Check if bounding boxes overlap (necessary but not sufficient for crossing)
      const overlaps = !(b.left > a.right || b.right < a.left ||
                         b.top > a.bottom || b.bottom < a.top);
      if (overlaps) {
        // Compute overlap area ratio -- small overlap more likely a crossing,
        // large overlap means parallel paths
        const overlapWidth = Math.min(a.right, b.right) - Math.max(a.left, b.left);
        const overlapHeight = Math.min(a.bottom, b.bottom) - Math.max(a.top, b.top);
        const overlapArea = Math.max(0, overlapWidth) * Math.max(0, overlapHeight);
        const minArea = Math.min(
          (a.right - a.left) * (a.bottom - a.top),
          (b.right - b.left) * (b.bottom - b.top)
        );
        // If overlap is small relative to edge size, likely a crossing not parallelism
        if (minArea > 0 && overlapArea / minArea < 0.5) {
          crossings++;
        }
      }
    }
  }

  return { edgeCount, estimatedCrossings: crossings };
})();
```

**Why bounding box, not geometric intersection:** True SVG path intersection requires parsing `d` attributes, sampling points along cubic bezier curves, and testing line segment intersections. Libraries like `svg-intersections` (github.com/signavio/svg-intersections) can do this but would need to be loaded into the page. The bounding box heuristic is 90% as useful and zero-dependency.

### 3.3 Label Truncation Detection

**Confidence: HIGH** -- standard DOM measurement technique

```javascript
// browser_evaluate script -- label truncation
(() => {
  const svg = document.querySelector('#output svg');
  if (!svg) return { error: 'No SVG found' };

  const nodes = svg.querySelectorAll('.node');
  let truncatedLabels = 0;
  let totalLabels = 0;
  const truncationDetails = [];

  nodes.forEach(node => {
    // With htmlLabels: true, labels are in foreignObject > div
    const foreignObjects = node.querySelectorAll('foreignObject');
    foreignObjects.forEach(fo => {
      const div = fo.querySelector('div, span, p');
      if (!div) return;
      totalLabels++;

      const foRect = fo.getBoundingClientRect();
      const textRect = div.getBoundingClientRect();

      // Check if text overflows its foreignObject container
      if (textRect.width > foRect.width + 2 || textRect.height > foRect.height + 2) {
        truncatedLabels++;
        truncationDetails.push({
          text: div.textContent.trim().substring(0, 50),
          containerWidth: foRect.width,
          textWidth: textRect.width
        });
      }
    });

    // Fallback for htmlLabels: false (SVG text elements)
    const textEls = node.querySelectorAll('text');
    textEls.forEach(t => {
      totalLabels++;
      // For SVG text, check if it extends beyond the node shape
      const shape = node.querySelector('rect, polygon, circle, ellipse');
      if (shape) {
        const shapeRect = shape.getBoundingClientRect();
        const textRect = t.getBoundingClientRect();
        if (textRect.width > shapeRect.width + 4) {
          truncatedLabels++;
        }
      }
    });
  });

  return { totalLabels, truncatedLabels, truncationDetails };
})();
```

### 3.4 Node Spacing Measurement

**Confidence: HIGH** -- standard bounding box measurement

```javascript
// browser_evaluate script -- node spacing
(() => {
  const svg = document.querySelector('#output svg');
  if (!svg) return { error: 'No SVG found' };

  const nodes = Array.from(svg.querySelectorAll('.node'));
  const rects = nodes.map(n => {
    const r = n.getBoundingClientRect();
    return {
      cx: (r.left + r.right) / 2,
      cy: (r.top + r.bottom) / 2,
      width: r.width,
      height: r.height,
      left: r.left,
      right: r.right,
      top: r.top,
      bottom: r.bottom
    };
  });

  // Find minimum spacing between any two adjacent nodes
  let minSpacing = Infinity;
  let avgSpacing = 0;
  let spacingCount = 0;

  for (let i = 0; i < rects.length; i++) {
    for (let j = i + 1; j < rects.length; j++) {
      const a = rects[i];
      const b = rects[j];
      // Gap = minimum edge-to-edge distance (not center-to-center)
      const hGap = Math.max(0, Math.max(b.left - a.right, a.left - b.right));
      const vGap = Math.max(0, Math.max(b.top - a.bottom, a.top - b.bottom));
      const gap = Math.sqrt(hGap * hGap + vGap * vGap);

      // Only consider "adjacent" nodes (gap < 200px -- not across the diagram)
      if (gap < 200) {
        minSpacing = Math.min(minSpacing, gap);
        avgSpacing += gap;
        spacingCount++;
      }
    }
  }

  return {
    minSpacing: minSpacing === Infinity ? 0 : Math.round(minSpacing),
    avgSpacing: spacingCount > 0 ? Math.round(avgSpacing / spacingCount) : 0,
    nodeCount: nodes.length
  };
})();
```

### 3.7 Comprehensive Extraction Script

All individual metrics combined into a single `browser_evaluate` call for efficiency:

```javascript
// FULL METRIC EXTRACTION -- single browser_evaluate call
(() => {
  const svg = document.querySelector('#output svg');
  if (!svg) return JSON.stringify({ error: 'No SVG rendered', score: 0 });

  // --- Node count ---
  const nodes = Array.from(svg.querySelectorAll('.node'));
  const nodeCount = nodes.length;

  // --- Edge count and crossing heuristic ---
  const edgePaths = Array.from(svg.querySelectorAll('.edgePath path, .flowchart-link'));
  const edgeCount = edgePaths.length;
  const edgeBoxes = edgePaths.map(p => p.getBoundingClientRect());
  let crossings = 0;
  for (let i = 0; i < edgeBoxes.length; i++) {
    for (let j = i + 1; j < edgeBoxes.length; j++) {
      const a = edgeBoxes[i], b = edgeBoxes[j];
      const oW = Math.min(a.right, b.right) - Math.max(a.left, b.left);
      const oH = Math.min(a.bottom, b.bottom) - Math.max(a.top, b.top);
      if (oW > 0 && oH > 0) {
        const oArea = oW * oH;
        const minA = Math.min(a.width * a.height, b.width * b.height);
        if (minA > 0 && oArea / minA < 0.5) crossings++;
      }
    }
  }

  // --- Label truncation ---
  let truncated = 0, totalLabels = 0;
  nodes.forEach(n => {
    n.querySelectorAll('foreignObject').forEach(fo => {
      const div = fo.querySelector('div, span, p');
      if (!div) return;
      totalLabels++;
      const foR = fo.getBoundingClientRect(), tR = div.getBoundingClientRect();
      if (tR.width > foR.width + 2 || tR.height > foR.height + 2) truncated++;
    });
  });

  // --- Node spacing ---
  const nodeRects = nodes.map(n => n.getBoundingClientRect());
  let minSpacing = Infinity;
  for (let i = 0; i < nodeRects.length; i++) {
    for (let j = i + 1; j < nodeRects.length; j++) {
      const a = nodeRects[i], b = nodeRects[j];
      const hGap = Math.max(0, Math.max(b.left - a.right, a.left - b.right));
      const vGap = Math.max(0, Math.max(b.top - a.bottom, a.top - b.bottom));
      const gap = Math.sqrt(hGap * hGap + vGap * vGap);
      if (gap < 200) minSpacing = Math.min(minSpacing, gap);
    }
  }

  // --- Diagram dimensions ---
  const svgRect = svg.getBoundingClientRect();
  const vw = window.innerWidth, vh = window.innerHeight;

  // --- Font size ---
  let tooSmall = 0, textCount = 0, smallest = Infinity;
  svg.querySelectorAll('foreignObject div, foreignObject p, text').forEach(el => {
    const fs = parseFloat(window.getComputedStyle(el).fontSize);
    if (fs > 0) { textCount++; smallest = Math.min(smallest, fs); if (fs < 12) tooSmall++; }
  });

  return JSON.stringify({
    nodeCount, edgeCount, crossings,
    truncated, totalLabels,
    minSpacing: minSpacing === Infinity ? 0 : Math.round(minSpacing),
    diagramWidth: Math.round(svgRect.width),
    diagramHeight: Math.round(svgRect.height),
    viewportWidth: vw, viewportHeight: vh,
    fitsInViewport: svgRect.width <= vw && svgRect.height <= vh,
    tooSmallFonts: tooSmall, textCount,
    smallestFont: smallest === Infinity ? 0 : smallest
  });
})();
```

## 4. Scoring Algorithm

### 4.1 Research-Backed Thresholds

**Confidence: HIGH** -- sourced from mermaid-sonar (Kwon et al. 2020, McCabe 1976, Miller's Law)

| Metric | Good | Acceptable | Bad | Source |
|--------|------|------------|-----|--------|
| Node count | 3-15 | 16-30 | 31+ | Miller's Law (7+/-2), mermaid-sonar (50 limit at density >0.3) |
| Edge count | <= nodes * 1.5 | <= nodes * 2 | > nodes * 2 | Graph density research (Kwon et al. 2020) |
| Edge crossings | 0 | 1-3 | 4+ | Visual clarity research -- crossings are the #1 readability killer |
| Cyclomatic complexity | < 5 | 5-10 | > 10 | McCabe (15 threshold for code; diagrams are stricter) |
| Label truncation | 0% | < 10% | > 10% | No truncation is always better |
| Min node spacing | > 30px | 15-30px | < 15px | Readability heuristic |
| Diagram fits viewport | Yes | One axis overflows | Both axes overflow | Legibility without scrolling |
| Font size | All >= 14px | All >= 12px | Any < 12px | WCAG readability guidelines |
| Max branch width | <= 5 | 6-8 | > 8 | Miller's Law, mermaid-sonar |

### 4.2 PDE-Specific Thresholds

PDE flows.md generates `flowchart TD` diagrams with specific patterns:
- Node IDs prefixed with journey number (J1_, J2_)
- Decision nodes use `{curly braces}` (diamond shape)
- Error nodes styled with `fill:#fee,stroke:#c33`
- Minimum per journey: 3 screen nodes, 1 decision, 1 error
- Edge labels use `-->|label|` syntax

**PDE-specific good diagram:** 5-12 nodes per journey, 1-3 decision points, clear happy path with 1-2 error branches. Total flow document may have 15-40 nodes across all journeys.

**PDE-specific bad diagram:** 40+ nodes in a single flow, spaghetti edges between journeys, decision nodes with 4+ branches, unlabeled edges, error nodes without recovery paths.

### 4.3 Scoring Formula (0-100)

The score is computed as a weighted sum of sub-scores, each normalized to 0-1:

```
SCORE = floor(
  nodeScore      * 25 +    // Node count appropriateness
  edgeDensity    * 20 +    // Edge-to-node ratio
  crossingScore  * 20 +    // Edge crossing penalty
  labelScore     * 15 +    // Label readability (truncation + font size)
  spacingScore   * 10 +    // Node spacing adequacy
  viewportScore  * 10      // Fits in viewport
)
```

**Sub-score calculations:**

```javascript
// nodeScore: peaks at 8-15 nodes, degrades outside
function nodeScore(count) {
  if (count === 0) return 0;
  if (count >= 5 && count <= 15) return 1.0;
  if (count >= 3 && count <= 20) return 0.8;
  if (count >= 1 && count <= 30) return 0.5;
  return Math.max(0, 1 - (count - 30) / 50);  // linear decay beyond 30
}

// edgeDensity: ratio of edges to nodes (ideal ~1.2-1.5)
function edgeDensityScore(edges, nodes) {
  if (nodes === 0) return 0;
  const ratio = edges / nodes;
  if (ratio >= 1.0 && ratio <= 1.5) return 1.0;
  if (ratio >= 0.8 && ratio <= 2.0) return 0.8;
  if (ratio >= 0.5 && ratio <= 2.5) return 0.5;
  return 0.2;
}

// crossingScore: 0 crossings = perfect, degrades fast
function crossingScore(crossings, edgeCount) {
  if (edgeCount === 0) return 1.0;
  if (crossings === 0) return 1.0;
  if (crossings <= 2) return 0.7;
  if (crossings <= 5) return 0.4;
  return Math.max(0, 0.3 - crossings * 0.03);
}

// labelScore: combines truncation and font size
function labelScore(truncated, totalLabels, tooSmallFonts, textCount) {
  const truncRatio = totalLabels > 0 ? 1 - (truncated / totalLabels) : 1;
  const fontRatio = textCount > 0 ? 1 - (tooSmallFonts / textCount) : 1;
  return truncRatio * 0.6 + fontRatio * 0.4;
}

// spacingScore: minimum spacing between nodes
function spacingScore(minSpacing) {
  if (minSpacing >= 30) return 1.0;
  if (minSpacing >= 20) return 0.8;
  if (minSpacing >= 10) return 0.5;
  return 0.2;
}

// viewportScore: does diagram fit?
function viewportScore(dWidth, dHeight, vWidth, vHeight) {
  const wRatio = Math.min(1, vWidth / dWidth);
  const hRatio = Math.min(1, vHeight / dHeight);
  return (wRatio + hRatio) / 2;
}
```

### 4.4 Score Interpretation

| Range | Meaning | PDE Action |
|-------|---------|------------|
| 85-100 | Excellent -- clear, readable, well-structured | No optimization needed |
| 70-84 | Good -- minor issues, generally readable | Low-priority optimization |
| 50-69 | Acceptable -- some readability concerns | Experiment should try to improve |
| 30-49 | Poor -- significant readability issues | Flows.md guidance likely needs improvement |
| 0-29 | Bad -- unreadable, too complex or broken | Parse error or severely over-complex |

### 4.5 Good Complexity vs Bad Complexity

**Confidence: HIGH** -- derived from PDE flows.md requirements analysis

PDE needs to distinguish:

| Good Complexity | Bad Complexity |
|-----------------|----------------|
| Multiple journeys with clear separation | All journeys tangled in one graph |
| Decision nodes with 2-3 branches | Decision nodes with 5+ branches |
| Error nodes with recovery paths | Orphan error nodes (dead ends) |
| Labeled edges on all decisions | Unlabeled edges between nodes |
| Subgraph grouping per journey | Flat graph with 40+ nodes |
| 3-8 nodes per journey segment | 15+ nodes in a linear chain |

The scoring algorithm handles this naturally:
- **Multiple small journeys** score well on nodeScore (each journey 5-12 nodes) and crossingScore (isolated subgraphs do not cross)
- **Spaghetti graphs** score poorly on crossingScore and edgeDensity
- **Too-simple graphs** (< 3 nodes) score poorly on nodeScore (missing minimum content)
- **Overly complex graphs** (30+ nodes) score poorly on nodeScore and viewportScore

## 5. PDE flows.md Context

### 5.1 What flows.md Generates

PDE's `/pde:flows` command generates Mermaid flowcharts with this structure:

1. **Overview diagram** -- `flowchart TD` hub-and-spoke showing all journeys from product entry
2. **Per-journey diagrams** -- `flowchart TD` with screen nodes (`J{N}_{step}["Label"]`), decision nodes (`J{N}_{step}{"Label?"}`), and error nodes (`J{N}_ERR{n}["Error"]`)
3. **Experience products** additionally generate: Temporal Flow (LR), Spatial Flow (TD), Social Flow (TD)
4. **Business products** additionally generate: Service Blueprint (sequenceDiagram), Growth Funnel (flowchart LR)

### 5.2 Common Quality Issues in Generated Flows

| Issue | How It Manifests | Metric Impact |
|-------|------------------|---------------|
| Too many nodes | 20+ nodes per journey | nodeScore degrades, viewport overflow |
| Unclear edge labels | Missing `-->&#124;label&#124;` on decision branches | Not directly measured (future: count unlabeled edges from decisions) |
| Spaghetti between journeys | Cross-journey edges without subgraph isolation | crossingScore degrades sharply |
| Label overflow | Long screen names like "User Profile Settings & Preferences Dashboard" | truncation count increases |
| Missing error paths | Decision nodes with only happy path | Not measured by visual metric (structural analysis needed) |
| Excessive detail | Every microinteraction as a node | nodeScore and viewportScore degrade |

### 5.3 What mermaid-metric.cjs Cannot Measure (Structural Limits)

These require parsing the Mermaid source text, not the rendered SVG:

- Whether all decision nodes have labeled branches
- Whether error nodes have recovery paths
- Whether node IDs follow PDE naming conventions (J{N}_ prefix)
- Whether transitions include motion annotations
- Cyclomatic complexity (easier to compute from graph structure than rendered SVG)

**Recommendation:** Consider a future `bin/mermaid-structure-metric.cjs` that parses the Mermaid text directly (regex or `mermaid.parse()`) for structural quality, complementing the visual metric.

## 6. Implementation Blueprint for bin/mermaid-metric.cjs

### 6.1 Script Flow

```
1. Parse argv[1] as file path
2. Read file, extract all ```mermaid fenced blocks
3. For each block (or combined):
   a. Generate temp HTML with Mermaid CDN + definition
   b. Write to /tmp/mermaid-metric-{hash}.html
   c. Start local server (if file:// blocked) OR use file:// URL
   d. browser_navigate to URL
   e. browser_wait_for SVG render completion
   f. browser_evaluate comprehensive metric extraction
   g. Parse JSON result
4. Compute weighted score from metrics
5. Print score to stdout (integer 0-100)
6. Exit 0 (always -- per VMET-06)
```

### 6.2 Degradation (No Playwright)

Per VMET-07, when Playwright is unavailable:
- Skip rendering entirely
- Parse Mermaid text with regex to count nodes and edges
- Compute a text-only score (node count heuristic)
- Print 0 (or the text-only score) and exit 0

### 6.3 Multiple Diagrams in One File

PDE flows.md contains multiple Mermaid blocks (overview + per-journey). The metric should:
- Extract all fenced mermaid blocks
- Render each independently
- Score each independently
- Return the **average** score (not the worst -- one complex overview is fine if journeys are clean)

### 6.4 Important: mermaid-metric.cjs is a Workflow Script, Not a Direct Runner

Because `mermaid-metric.cjs` runs as a Node.js script invoked by the experiment runner, it cannot directly call Playwright MCP tools (those are Claude-facing tools). The script must instead:

1. Generate the HTML wrapper file
2. Output instructions or invoke a helper that uses Playwright programmatically

**Two viable architectures:**

**Option A (Recommended): Script generates HTML, Claude orchestrates Playwright**
- `mermaid-metric.cjs` extracts Mermaid blocks, generates the HTML wrapper, writes it to disk
- The experiment runner (or the calling workflow) handles `browser_navigate` + `browser_evaluate`
- The metric script receives the evaluation result via stdin or a temp file
- This matches the existing `_evalMetric` contract where the script is the final scorer

**Option B: Script uses Playwright Node.js API directly**
- `mermaid-metric.cjs` imports `playwright` (the npm package, not the MCP server)
- Launches a headless browser, navigates to the HTML file, evaluates the metric script
- Returns the score
- Downside: requires `playwright` npm dependency; upside: self-contained

**Recommendation:** Use Option A to align with the Playwright MCP architecture already established in Phase 108. The metric script does the computation; Playwright MCP handles the browser.

### Gaps and Open Questions

1. **CSS class case sensitivity:** One source reports `.edgePath` becomes `.edgepath` in the DOM. Need live verification in Phase 110. Mitigation: use `svg.querySelectorAll('[class*="edgePath"], [class*="edgepath"]')` or test both.

2. **htmlLabels behavior:** Mermaid v11 defaults to `htmlLabels: true` which uses `<foreignObject>`. The metric scripts handle both paths but should be tested with both settings.

3. **Multiple Mermaid blocks performance:** Rendering 4-6 Mermaid diagrams sequentially via Playwright will be slow (each requires navigate + render + evaluate). Consider rendering all blocks in a single HTML page with multiple containers.

4. **Viewport size for scoring:** What viewport should mermaid-metric.cjs use? Recommendation: 1280x800 (standard laptop) to match typical developer viewing context. This should be configurable.

5. **Mermaid version pinning:** Using `@11` gets latest v11.x automatically. For reproducible metrics, consider pinning to a specific version (e.g., `@11.12.3`). However, this adds maintenance burden. Recommendation: use `@11` and accept minor variation.

6. **Dagre vs ELK layout:** Mermaid defaults to Dagre. ELK produces better layouts but requires additional configuration. The metric should measure what Mermaid produces by default (Dagre) since that matches what users see.
