## 1. Multi-Candidate Optimization Patterns

### 1.1 How Evolutionary Algorithms Handle Population-Based Search

Evolutionary algorithms (EAs) maintain a **population** of candidate solutions evaluated in parallel per generation. The core loop is: generate N offspring via mutation/crossover, evaluate each with a fitness function, select survivors for the next generation. PDE's experiment runner is already a (1+1) evolutionary strategy -- one parent, one offspring, keep the better. Extending to (1+N) (one parent, N offspring, keep best) is the minimal and correct extension for PDE's constraints.

**Why (1+N) and not (N+N):** Full population-based EAs (genetic algorithms with population sizes of 50-100+) are designed for multi-dimensional continuous optimization with crossover operators. PDE's search space is *prose text mutations* evaluated by an LLM -- crossover between two prose variants is undefined and dangerous. The (1+N) strategy preserves PDE's existing single-parent lineage while gaining the diversity benefit of sampling multiple mutations per iteration.

### 1.2 Selection Strategy: Use Best-of-N (Deterministic)

Three common selection strategies from EA literature:

| Strategy | How It Works | Fit for PDE? |
|----------|-------------|--------------|
| **Best-of-N (truncation)** | Score all N, keep the single best | YES -- simple, deterministic, matches existing keep/discard logic |
| **Tournament selection** | Randomly pair candidates, winners advance | NO -- requires population continuity across generations (PDE has single lineage) |
| **Roulette wheel (proportional)** | Selection probability proportional to fitness | NO -- adds stochastic noise, no benefit for single-winner scenario |

**Recommendation: Best-of-N with deterministic selection.** Generate N candidates, score each via the existing `_evalMetric` contract, keep the one with the best score (respecting `direction: max` or `direction: min`). This is equivalent to the existing `_compareMetric` function called N times with an argmax/argmin over the results.

This aligns with best-of-N sampling research from LLM alignment (Coste et al. 2025, "Evaluation of Best-of-N Sampling Strategies") which shows deterministic top-1 selection is optimal when the evaluation function is reliable (no reward hacking concern in PDE's case since metrics are structural, not learned reward models).

### 1.3 Population Size: N=2-3 for Expensive Eval Functions

EA literature consistently shows: **the fewer function evaluations available, the lower population sizes perform better.** For PDE's visual experiments where each evaluation requires browser rendering (30s+), the cost constraint dominates.

| N | Time per Iteration (30s eval) | Mutation Tokens | Sweet Spot |
|---|-------------------------------|-----------------|------------|
| 1 | 30s | 1x | Text-only experiments (fast eval) |
| 2 | 60s | 2x | Default for visual experiments |
| 3 | 90s | 3x | Maximum practical for visual experiments |
| 5+ | 150s+ | 5x+ | Only for sub-second eval functions |

**Recommendation: Default N=1 (backward compatible), typical visual experiments use N=2, maximum N=3.** The marginal gain from N=2 to N=3 is much smaller than from N=1 to N=2 (diminishing returns from order statistics). N=2 doubles the chance of finding an improvement per iteration at 2x cost -- net positive because it avoids wasted iterations where the single mutation was unlucky.

**Key insight from best-of-N research:** The expected improvement from best-of-N sampling scales approximately as O(sqrt(log N)) for well-behaved distributions. Going from N=1 to N=2 captures most of the benefit. Going from N=2 to N=3 adds roughly 25% more expected improvement at 50% more cost. N=3 is the practical ceiling for expensive evaluations.

### 1.4 When Multi-Candidate Is Worth the Cost

| Phase of Optimization | Recommendation | Rationale |
|----------------------|----------------|-----------|
| **Early exploration** (iterations 1-5) | N=2-3 | High variance in mutation quality; multiple samples avoid wasting iterations on poor mutations |
| **Mid optimization** (iterations 6-15) | N=2 | Moderate variance; still beneficial but diminishing |
| **Late refinement** (iterations 15+) | N=1 | Low variance; mutations are small tweaks, single candidate sufficient |

An adaptive scheme (start with N=3, reduce to N=1 after K consecutive KEEPs) would be elegant but adds complexity. **For v0.14, use static N from frontmatter.** Adaptive N is a future optimization.

## 2. Adapting PDE's Keep/Discard Loop

### 2.1 Current Loop (Single Candidate)

From `workflows/optimize.md` Step 7 and `bin/lib/experiment-runner.cjs`:

```
For each iteration:
  1. Agent mutates mutable_files (one mutation)
  2. _checkModifiedFiles validates boundary compliance
  3. _evalMetric runs verify command -> metric_value
  4. _compareMetric determines KEEP or DISCARD
  5. If KEEP: _commit (git add + commit, update EXPERIMENT-BEST.json)
  6. If DISCARD: _reset (git reset --hard HEAD~1)
  7. If CRASH: _reset + increment failure counter
  8. Write JSONL row
```

### 2.2 New Loop (Multi-Candidate)

```
For each iteration:
  1. For candidate_index = 1..N:
     a. If candidate_index > 1: _reset to iteration baseline
     b. Agent mutates mutable_files (mutation variant candidate_index)
     c. _checkModifiedFiles validates boundary compliance
     d. _evalMetric runs verify command -> candidate_scores[candidate_index]
     e. _commit with temporary commit message
     f. Store candidate_commit_sha
  2. Find best_candidate = argmax/argmin(candidate_scores) excluding CRASHed candidates
  3. If no candidates succeeded: status = CRASH, _reset to iteration baseline
  4. If best_candidate found:
     a. _compareMetric(best_score, bestMetric, direction) -> KEEP or DISCARD
     b. If KEEP: reset to best_candidate_commit, update EXPERIMENT-BEST.json
     c. If DISCARD: _reset to iteration baseline
  5. Write JSONL row with extended fields
```

### 2.3 Git State Management Per Candidate

**Critical constraint:** PDE operates on a single `experiment/{slug}` branch. No parallel git worktrees, no subprocesses. The agent is sequential.

**Recommended approach: Sequential evaluation with commit/reset (Option A with commits).**

Each candidate gets committed (so its state is recoverable), scored, then the branch is either kept at that commit or reset. After all N candidates are evaluated, the branch is reset to the best candidate's commit.

```
Iteration baseline = HEAD at start of iteration

Candidate 1:
  - Agent mutates files
  - git add -A && git commit -m "experiment({slug}): candidate 1"
  - _evalMetric -> score_1
  - candidate_1_sha = HEAD

Candidate 2:
  - git reset --hard {iteration_baseline}
  - Agent mutates files (different mutation prompt)
  - git add -A && git commit -m "experiment({slug}): candidate 2"
  - _evalMetric -> score_2
  - candidate_2_sha = HEAD

Select best:
  - git reset --hard {best_candidate_sha}
  - (Losing candidate commits become dangling and will be GC'd)
```

**Why not stash-based (Option C)?** Git stash doesn't create addressable commits -- you can't return to a stash after popping it without additional bookkeeping. Commits are the native unit of PDE's experiment state machine and they are inherently addressable.

**Why not parallel branches (Option B)?** Would require creating/deleting N branches per iteration. The existing `experiment.cjs` state machine is designed for a single `experiment/{slug}` branch. Adding branch-per-candidate would require significant refactoring of `_init`, `_commit`, `_reset`, `_promote`, and `_cleanup`. Not worth it for N=2-3.

### 2.4 Circuit Breakers with Multi-Candidate

Circuit breakers should apply **per iteration, not per candidate.** This matches the requirements doc (MULTI-03).

| Breaker | Behavior with Multi-Candidate |
|---------|------------------------------|
| `iteration_budget` | Counts iterations (not individual candidate evaluations) |
| `time_budget` | Wall clock includes all N candidate evaluations per iteration |
| `consecutive_failures` | Increments only if ALL N candidates in an iteration fail (CRASH or DISCARD) |
| `no_progress` | Increments if no candidate in the iteration beats bestMetric |
| `visual_regression_guard` | Checked against the winning candidate only (losers are discarded) |

**Partial batch handling:** If some candidates CRASH and others succeed, the iteration is NOT a failure. The surviving candidates compete normally. Only if ALL candidates CRASH does the iteration count as a CRASH for circuit breaker purposes.

Example: N=3, candidate 1 CRASHes, candidate 2 scores 75, candidate 3 scores 82.
- best_candidate = candidate 3 (score 82)
- Compare 82 vs bestMetric: if better, KEEP; if worse, DISCARD
- consecutiveFailures is NOT incremented (at least one candidate succeeded)

## 3. Git Branch Strategy Recommendation

### 3.1 Detailed Comparison

| Strategy | Complexity | Fits PDE State Machine? | Risk |
|----------|-----------|------------------------|------|
| **A: Sequential commit/reset** | Low | YES -- uses existing `_commit` and `_reset` | Dangling commits (harmless, GC'd) |
| **B: Parallel branches** | High | NO -- requires new branch management | Branch proliferation, cleanup complexity |
| **C: Git stash** | Medium | NO -- stash not addressable like commits | Stash stack corruption, no SHA tracking |

### 3.2 Recommendation: Sequential Commit/Reset (Option A)

Use the existing `experiment.cjs` primitives with minimal extension:

1. **New helper: `_resetToSha(cwd, slug, sha)`** -- wraps `git reset --hard {sha}` with the existing safety guards (verify on correct branch, verify prefix). This is a generalization of `_reset` which currently only resets HEAD~1.

2. **New helper: `_getCurrentSha(cwd)`** -- wraps `git rev-parse HEAD` (already available via `execGit`).

3. **Orchestrator logic:** The optimize.md workflow handles candidate iteration and selection. The runner agent only handles single-candidate mutation (no change to runner agent). The orchestrator dispatches the runner N times per iteration, captures results, and selects the best.

**Key architectural decision:** The multi-candidate loop lives in the **orchestrator** (optimize.md), NOT in the runner agent or experiment-runner.cjs. This keeps the runner agent stateless (it just mutates and returns) and keeps experiment-runner.cjs under its 300-line ceiling.

### 3.3 Implementation in optimize.md Step 7

The existing Step 7 loop dispatches one `Task()` per iteration. For multi-candidate:

```
For each iteration:
  iteration_baseline_sha = $(git rev-parse HEAD)
  candidate_results = []

  For candidate_index = 1..N:
    If candidate_index > 1:
      git reset --hard {iteration_baseline_sha}

    Dispatch Task() to runner agent (same as current, but with candidate_index context)

    Parse result: { status, metric_value, description }

    If status == KEEP or status == DISCARD:
      candidate_sha = $(git rev-parse HEAD)
      candidate_results.push({ index: candidate_index, status, metric_value, sha: candidate_sha })
    Else (CRASH/BOUNDARY_VIOLATION):
      git reset --hard {iteration_baseline_sha}
      candidate_results.push({ index: candidate_index, status: 'CRASH', metric_value: null, sha: null })

  // Select best from surviving candidates
  surviving = candidate_results.filter(c => c.metric_value !== null)

  If surviving.length == 0:
    // All crashed -- treat as iteration CRASH
    git reset --hard {iteration_baseline_sha}
    iteration_status = 'CRASH'
  Else:
    best = argmax/argmin(surviving, direction)
    decision = _compareMetric(best.metric_value, bestMetric, direction)

    If decision == 'KEEP':
      git reset --hard {best.sha}
      iteration_status = 'KEEP'
    Else:
      git reset --hard {iteration_baseline_sha}
      iteration_status = 'DISCARD'
```

When `candidates: 1`, this reduces to exactly the current behavior (no candidate loop, single Task dispatch).

## 4. JSONL Schema Extension

### 4.1 Current Schema (experiment-schema.cjs)

```javascript
const JSONL_ROW_FIELDS = Object.freeze([
  'id', 'iteration', 'ts', 'commit', 'metric_value',
  'metric_delta', 'status', 'description', 'tokens_used',
]);
```

### 4.2 Extended Schema

Add three new fields at the end of the array to maintain backward compatibility:

```javascript
const JSONL_ROW_FIELDS = Object.freeze([
  'id', 'iteration', 'ts', 'commit', 'metric_value',
  'metric_delta', 'status', 'description', 'tokens_used',
  // Multi-candidate extensions (v0.14)
  'candidates_evaluated',   // number: how many candidates were scored this iteration
  'candidates_scores',      // array|null: scores of all candidates [82, 75, null] (null = crash)
  'best_candidate_index',   // number|null: 0-indexed position of winning candidate
]);
```

### 4.3 Backward Compatibility

When `candidates: 1` (default):
- `candidates_evaluated` = 1
- `candidates_scores` = [metric_value] (single-element array)
- `best_candidate_index` = 0

When reading old JSONL files that lack these fields, consumers treat missing fields as:
- `candidates_evaluated` = 1 (implied single candidate)
- `candidates_scores` = null (not recorded)
- `best_candidate_index` = null (not recorded)

The `_writeJsonlRow` function already handles missing fields gracefully (sets to null). No changes to the write function are needed -- just extend JSONL_ROW_FIELDS and pass the new fields in rowData.

### 4.4 Example JSONL Rows

**Single candidate (backward compatible):**

## 5. Cost and Performance Analysis

### 5.1 Per-Iteration Cost Model

| Factor | N=1 | N=2 | N=3 |
|--------|-----|-----|-----|
| Verify command runs | 1 | 2 | 3 |
| Wall clock (30s eval) | ~35s | ~65s | ~95s |
| Wall clock (5s eval, text-only) | ~8s | ~13s | ~18s |
| Mutation prompt tokens | ~2000 | ~4000 | ~6000 |
| Total tokens/iteration | ~2500 | ~5000 | ~7500 |

**Note:** The mutation prompt cost dominates for LLM-based experiments. Each candidate requires a separate `Task()` dispatch to the runner agent. The verify command cost is secondary but adds up for visual experiments with Playwright rendering.

### 5.2 Expected Value Analysis

For a typical visual experiment with 20% chance of improvement per candidate:

| N | P(at least one improvement) | Expected cost per improvement |
|---|---------------------------|------------------------------|
| 1 | 20% | 5 iterations (150s) |
| 2 | 36% | 2.8 iterations (182s) |
| 3 | 49% | 2.0 iterations (190s) |

**Insight:** N=2 finds improvements in fewer iterations but at similar wall-clock cost. The real benefit is **fewer total iterations consumed** from the iteration_budget. With a budget of 20 iterations, N=2 effectively searches twice as much of the space.

### 5.3 When to Use Each N

| Experiment Type | Recommended N | Rationale |
|----------------|---------------|-----------|
| Text-only (nyquist-metric) | 1 | Fast eval, budget not a bottleneck |
| Visual wireframe/mockup | 2 | 30s eval, iteration budget matters |
| Pipeline experiments | 1 | Very expensive eval (full pipeline run), N=2 doubles already-long iterations |
| A11y experiments | 2 | Moderate eval cost, benefits from diversity |
| Divergence experiments | 3 | Already generating multiple variants; evaluation is the bottleneck |
| Meta-experiments | 1 | Nested experiments are extremely expensive; minimize outer iterations |

## 6. Divergence Metric for Ideation (IDIV-01..03)

### 6.1 Problem Statement

Ideation produces multiple concept directions. We need to measure whether ideation guidance produces *diverse* concepts (high variance) vs convergent concepts (low variance). The divergence metric should work without npm dependencies.

### 6.2 Candidate Approaches

| Approach | Deps Required | Accuracy | Implementation Complexity |
|----------|--------------|----------|--------------------------|
| **File-size standard deviation** | None | Low-Medium | Trivial |
| **Screenshot SHA-256 comparison** | None (crypto built-in) | Binary only (same/different) | Low |
| **DOM structure comparison** | None (browser_evaluate) | Medium | Medium |
| **Perceptual hashing (pHash/dHash)** | npm image lib | High | High (violates zero-dep constraint) |
| **CSS property variance** | None (browser_evaluate) | Medium | Medium |
| **Pixel buffer comparison** | npm sharp/canvas | High | High (violates zero-dep constraint) |

### 6.3 Recommendation: File-Size StdDev + Hash Pairwise Uniqueness (Combined)

Use two complementary metrics that require zero npm dependencies:

**Primary: File-size standard deviation**
- Generate N wireframe HTML files from ideation output
- Measure file sizes: [12400, 8200, 15600] bytes
- Compute standard deviation: high StdDev = diverse, low StdDev = convergent
- Normalize: `divergence_score = stddev / mean * 100` (coefficient of variation)

**Secondary: SHA-256 pairwise uniqueness**
- Screenshot each wireframe via Playwright
- Compute SHA-256 hash of each screenshot PNG
- Count unique hashes: `unique_ratio = unique_hashes / total_screenshots`
- If all screenshots hash identically, divergence = 0 regardless of file-size variance

**Combined metric:**
```
divergence = (cv_score * 0.6) + (uniqueness_ratio * 100 * 0.4)
```

Where `cv_score` = coefficient of variation of file sizes, capped at 100. `uniqueness_ratio` = unique screenshot hashes / total screenshots.

### 6.4 Why File-Size Works as a Proxy

File size correlates with structural complexity. A wireframe with 3 sections, no images, and minimal copy will be ~5KB. A wireframe with 12 sections, placeholder images, and detailed copy will be ~20KB. If ideation produces concepts that all have similar complexity, file sizes cluster tightly (low StdDev). If concepts range from minimal to complex, file sizes spread (high StdDev).

**Limitations:**
- Two structurally different wireframes can have similar file sizes
- CSS whitespace differences can inflate size without visual difference
- Not a substitute for true perceptual comparison

**Why this is acceptable for v0.14:** The divergence metric is a proxy used to optimize ideation guidance. A rough proxy that works without dependencies is better than an accurate metric that requires `sharp` or `canvas` npm packages. If the metric drives ideation to produce more varied outputs (as measured by eyeball review), it is serving its purpose.

### 6.5 Minimum Sample Size

**Three concepts minimum** (matching IDIV-03 requirement). With N=2, standard deviation is volatile (single pairwise comparison). With N=3, you get three pairwise comparisons and a meaningful variance estimate. N=5 would be statistically stronger but requires 5 wireframe generations per evaluation -- too expensive.

**Practical implementation:** `bin/divergence-metric.cjs` generates 3 concept wireframes by running the ideation skill 3 times with different seed prompts, measures file sizes and screenshot hashes, outputs a single numeric divergence score.

### 6.6 Alternative: DOM Structure Similarity via browser_evaluate

For future improvement beyond v0.14, `browser_evaluate` can extract:
- Element count per semantic type (h1, h2, section, nav, img, button)
- CSS computed styles (color palette, font sizes, spacing values)
- DOM tree depth and breadth

These produce a structural fingerprint per wireframe. Pairwise Jaccard distance between fingerprints gives a more semantically meaningful diversity score. But this requires more complex CJS code and is better deferred to a future iteration of the divergence metric.

### 7.2 Git State Machine Extension

Add to `experiment.cjs`:

```javascript
function _resetToSha(cwd, slug, sha) {
  // Guard: verify on correct experiment branch
  const branchResult = execGit(cwd, ['rev-parse', '--abbrev-ref', 'HEAD']);
  if (branchResult.exitCode !== 0) return { reset: false, reason: 'git_error' };
  if (branchResult.stdout !== `experiment/${slug}`) return { reset: false, reason: 'wrong_branch' };

  // Guard: verify sha is an ancestor of current HEAD on this branch
  const mergeBaseResult = execGit(cwd, ['merge-base', '--is-ancestor', sha, 'HEAD']);
  // Note: also allow resetting to HEAD itself or forward commits from same branch

  const resetResult = execGit(cwd, ['reset', '--hard', sha]);
  if (resetResult.exitCode !== 0) return { reset: false, reason: 'reset_failed' };
  return { reset: true };
}
```

This is the only new git primitive needed. Everything else composes existing `_commit`, `_reset`, and `_compareMetric`.

## 8. Pitfalls and Risk Mitigation

### 8.1 Critical: Dangling Commits from Losing Candidates

**Risk:** Each iteration with N=3 creates 3 commits, 2 of which become dangling after `git reset --hard`. Over 20 iterations, that is 40 dangling commits.

**Mitigation:** Git GC handles this automatically. Dangling commits are pruned after `gc.pruneExpire` (default 2 weeks). No action needed, but document this in the experiment report.

### 8.2 Critical: Runner Agent Needs Candidate Differentiation

**Risk:** If the runner agent receives the same prompt for all N candidates, it may produce identical mutations (LLM determinism with same context).

**Mitigation:** Include `candidate_index` and a diversity instruction in the Task() prompt:
```
Candidate {candidate_index} of {N}. Generate a DIFFERENT mutation than previous candidates
in this iteration. Focus on: {varied_focus_area}.
```

The orchestrator should also vary the mutation focus per candidate (e.g., candidate 1 targets heading structure, candidate 2 targets landmark density, candidate 3 targets whitespace ratios).

### 8.3 Moderate: Reset Race Condition

**Risk:** If `_evalMetric` crashes *after* the commit but before the sha is recorded, the orchestrator loses track of the candidate commit.

**Mitigation:** Always capture SHA immediately after commit, before eval. The sequence must be: commit -> capture SHA -> eval. If eval crashes, the SHA is still recorded and can be reset to.

### 8.4 Moderate: Time Budget Consumed Faster

**Risk:** N=3 triples wall-clock time per iteration. A 60-minute time_budget with 30s eval reaches only ~40 iterations with N=1 but ~13 iterations with N=3.

**Mitigation:** Document in experiment.md template that `time_budget_minutes` should be increased proportionally to `candidates` count. The experiment-schema.cjs parser could emit a warning if `time_budget / iteration_budget / candidates < 1 minute`.

### 8.5 Minor: JSONL Array Field

**Risk:** `candidates_scores` is an array, which is unusual for JSONL (most fields are scalars). Some downstream consumers may not expect arrays.

**Mitigation:** JSON serialization handles arrays natively. The experiment-report.cjs generator just needs to handle the array when computing statistics. The JSONL spec has no restriction on array values.
