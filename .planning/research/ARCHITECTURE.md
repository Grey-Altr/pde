```
├── server-gen.cjs      # EXISTS -- stdio MCP server generator

bin/lib/
└── mcp-bridge.cjs      # MODIFY -- add loadDynamicServers() from registry.json

.planning/cli-anything/
├── registry.json       # EXISTS -- published CLI entries (gains 'status' + 'install_hint')
└── {slug}/

```

### Structure Rationale

- **`discover.cjs` separate from `help-parser.cjs`:** Discovery (finding binaries on the system) is a distinct concern from parsing (understanding what a binary does). Keeping them separate lets `discover.cjs` run at startup without triggering full capability parsing.
- **`registry.json` as the single source of truth:** Already established in v0.20. Discovery writes into it; `mcp-bridge.cjs` reads from it to register dynamic APPROVED_SERVERS entries. No new state files needed.
- **`references/app-integrations.md`:** Documents known design app CLIs (Blender, figma-export, Sketch, etc.) with their discovery hints and Python/pip status. Consumed by both `discover.cjs` logic and workflow narrative instructions.

## Architectural Patterns

### Pattern 1: App Discovery -> Registry -> MCP Registration

**What:** A five-step pipeline converts "app exists on system" into "tool available to executor agent."

**When to use:** Whenever a new desktop app or pip-installed CLI is to be exposed to executor agents.

**Steps:**
```
1. discover.cjs: probe candidate binary paths
       which blender
       mdfind "kMDItemCFBundleIdentifier=='org.blenderfoundation.blender'"  (macOS only)
       /Applications/Blender.app/Contents/MacOS/Blender  (well-known path fallback)
       -> resolves absolute binary path

2. help-parser.cjs: discoverCapabilities(binaryPath)
       -> CapabilitySchema[]

3. registry.cjs: upsertEntry(registryPath, { name, binary, server_path, status:'available' })
       -> .planning/cli-anything/registry.json updated

4. server-gen.cjs: writeServer(outDir, capabilities, meta, cwd)
       -> .planning/cli-anything/{slug}/server/server.cjs

5. mcp-bridge.cjs: loadDynamicServers(registryPath)
       -> APPROVED_SERVERS gains entry, TOOL_MAP gains {slug}:{capability} entries
```

**Trade-offs:**
- Pro: Fully self-contained; reuses all existing CLI-Anything infrastructure
- Pro: Only registers apps confirmed to exist -- avoids startup probe timeouts for absent apps
- Con: Newly discovered apps require session restart to activate in Claude Code's MCP runtime (no live hot-reload without `notifications/tools/list_changed` support from Claude Code host)

### Pattern 2: Python/pip Isolation via ENV-gated Venv

**What:** Each pip-installed CLI tool gets a dedicated Python virtual environment. The path is communicated via an environment variable, following the exact pattern established by `cad.cjs` with `CADQUERY_PYTHON`.

**When to use:** Any CLI that requires pip-installed dependencies (rembg pip CLI, TripoSR, Blender Python scripts, etc.).

**Existing pattern in cad.cjs (HIGH confidence -- read directly from source):**

```javascript
// cad.cjs -- established Python isolation pattern
const PYTHON_BIN_KEY = 'CADQUERY_PYTHON';
const DEFAULT_PYTHON = 'python3';

// Validate import works in the target env before using it
function checkCadQuery(pythonBin, _execFn) {
  try {
    // Uses execFileSync (safe -- no shell, no injection risk)
    _execFn(pythonBin, ['-c', 'import cadquery'], { encoding: 'utf8', timeout: 10000 });
    return true;
  } catch (_e) { return false; }
}
```

**Extension for new pip CLIs (discover.cjs):**

```javascript
// discover.cjs -- pip module availability check
// Uses spawnSync (file-based, not shell -- matches existing cad.cjs pattern)
function checkPipModule(toolName, pythonBin) {
  const bin = pythonBin || 'python3';
  const r = spawnSync(bin, ['-c', `import ${toolName}`], { encoding: 'utf8', timeout: 10000 });
  if (r.status === 0) return { available: true, pythonBin: bin };
  return { available: false, installHint: `pip install ${toolName}` };
}
```

**User venv setup pattern (same as existing CadQuery instructions in cad.cjs):**

```bash
python3.11 -m venv ~/pde-rembg-env
source ~/pde-rembg-env/bin/activate
pip install rembg
export REMBG_PYTHON=~/pde-rembg-env/bin/python3
```

**Zero-npm-deps compliance:** Plugin root never installs Python packages. Venv paths are user-configured env vars. `discover.cjs` only calls `spawnSync` (Node built-in) -- no npm packages required.

**Trade-offs:**
- Pro: Perfect isolation; conflicting deps between tools never collide
- Pro: Degrades gracefully -- env var unset falls back to system python3, returns actionable install message
- Con: User must create venvs manually; discovery must run import check to confirm deps installed (not just binary presence)

### Pattern 3: Design Workflow -> Wrapped App Tool Invocation

**What:** Design pipeline workflows invoke wrapped desktop app tools through the same `TOOL_MAP` canonical naming convention already used for Stitch, Figma, etc.

**When to use:** When a design workflow step benefits from a native app action (e.g., exporting a Blender scene as GLB, running a figma-export batch).

**Canonical name convention (consistent with existing TOOL_MAP):**

```
{slug}:{capability-name}  ->  mcp__{slug}__{raw_capability_name}
```

Examples:
```
blender:render          ->  mcp__blender__blender_render
figma-export:export     ->  mcp__figma_export__figma_export_export
sketch:export-artboards ->  mcp__sketch__sketch_export_artboards
```

**Workflow invocation (same pattern as Stitch checks in wireframe.md):**

```javascript
// In workflow step -- identical to existing Stitch usage
const { resolveToolName, probeServer } = require(
  `${process.env.CLAUDE_PLUGIN_ROOT}/bin/lib/mcp-bridge.cjs`
);
const available = probeServer('blender');
if (available) {
  // executor agent calls: mcp__blender__blender_render
} else {
  // degrade: skip 3D step, document in DESIGN-STATE.md
}
```

**Trade-offs:**
- Pro: No new conventions -- TOOL_MAP + probe/degrade already understood by all workflows
- Con: TOOL_MAP entries must be generated from registry at load time for dynamic apps (cannot be fully hardcoded for user-installed apps)

### Pattern 4: `pde-tools app` Subcommand (New Top-Level Entry Point)

**What:** A new `app` subcommand in `pde-tools.cjs` provides a single user-facing entry point for all desktop app operations.

**Commands:**

```
pde-tools app discover              # scan system, populate registry
pde-tools app discover --only blender sketch  # scope to specific known apps
pde-tools app wrap <binary>         # wrap arbitrary binary (alias for cli-anything wrap + register)
pde-tools app register <slug>       # add existing wrapped CLI to mcp-bridge dynamic list
pde-tools app list                  # show all registered app tools with status
pde-tools app probe <slug>          # test that server launches and tools respond
```

**When to use:** Slash commands (`/pde:wrap`, `/pde:app-discover`) and workflow steps call `pde-tools app` rather than lower-level `cli-anything` subcommands directly.

## Data Flow

### "App Detected on System" -> "Tool Available to Executor Agent"

```
[User runs /pde:wrap blender  OR  pde-tools app discover triggered]
    |
    v
discover.cjs: resolveDesktopApp('blender')
  1. Check process.env.BLENDER_BIN  (explicit override, all platforms)
  2. spawnSync('which', ['blender'])  (PATH, cross-platform, no shell injection)
  3. mdfind "kMDItemCFBundleIdentifier=='org.blenderfoundation.blender'"  (macOS)
  4. Well-known path: /Applications/Blender.app/Contents/MacOS/Blender
  -> resolves: /Applications/Blender.app/Contents/MacOS/Blender
    |
    v
help-parser.cjs: discoverCapabilities(resolvedPath)
  spawnSync(binary, ['--help'], { timeout: 5000 })  -- no shell, safe
  -> parseSubcommands() + parseFlags()
  -> CapabilitySchema[] e.g. { name:'blender_render', path:'--render-anim', ... }
    |
    v
model.cjs: validateCapabilityModel({ meta: { source, type:'cli', ... }, capabilities })
    |
    v
server-gen.cjs: writeServer(outDir, capabilities, meta, cwd)
  -> .planning/cli-anything/blender/server/server.cjs  (stdio MCP server)
  -> .planning/cli-anything/blender/server/SKILL.md
    |
    v
registry.cjs: upsertEntry(registryPath, {
  name: 'blender', binary: '/Applications/.../Blender',
  capabilities_count: N, server_path, status: 'available'
})
  -> .planning/cli-anything/registry.json updated
    |
    v
mcp-bridge.cjs: loadDynamicServers(registryPath)  [called at workflow init]
  -> APPROVED_SERVERS['blender'] = { transport:'stdio', serverPath, probeTimeoutMs:15000 }
  -> TOOL_MAP['blender:render'] = 'mcp__blender__blender_render'
    |
    v
[Claude Code session restart activates the new server]
    |
    v
Executor agent in wireframe.md or mockup.md:
  resolveToolName('blender:render') -> 'mcp__blender__blender_render'
  Calls: mcp__blender__blender_render({ file:'scene.blend', output:'/tmp/render.png' })
```

### Python pip CLI Flow (e.g., rembg as pip CLI)

```
[User sets REMBG_PYTHON=~/pde-rembg-env/bin/python3]
    |
    v
discover.cjs: checkPipModule('rembg', process.env.REMBG_PYTHON)
  spawnSync(pythonBin, ['-c', 'import rembg'], { timeout: 10000 })
  -> succeeds  OR  { available: false, installHint: 'pip install rembg' }
    |
    v
  if available:
    Effective binary: pythonBin + args ['-m', 'rembg', ...]
    server-gen.cjs: generatePythonModuleHandler()  -- new variant
      -> server.cjs spawns: spawnSync(pythonBin, ['-m', 'rembg', ...args])
    -> same registry + TOOL_MAP pipeline as binary app flow above
    |
    v
  if unavailable:
    registry.cjs: upsertEntry({ name:'rembg', status:'unavailable',
      install_hint:'python3 -m venv ~/pde-rembg-env && pip install rembg' })
    -> design workflows read this and degrade gracefully
```

### Design Pipeline Workflow -> App Tool Invocation


## Python/pip Isolation Strategy

### Zero-npm-deps Compliance

The plugin root constraint (zero npm deps) is maintained because:

1. No npm package wraps Python -- Node's built-in `child_process.spawnSync` calls Python directly
2. No `requirements.txt` at plugin root -- each pip tool has its own external venv
3. Discovery only requires `process.env` lookup + `spawnSync` (both Node built-ins)

### Env Var Convention (extends existing cad.cjs pattern)

| Tool | Env Var | Default | Recommended Venv Path |
|------|---------|---------|----------------------|
| CadQuery (existing) | `CADQUERY_PYTHON` | `python3` | `~/cadquery-env/bin/python3` |
| rembg pip CLI | `REMBG_PYTHON` | `python3` | `~/pde-rembg-env/bin/python3` |
| TripoSR | `TRIPOSR_PYTHON` | `python3` | `~/pde-triposr-env/bin/python3` |
| Any new pip CLI | `{TOOL_UPPER}_PYTHON` | `python3` | `~/pde-{tool}-env/bin/python3` |
| Blender native binary | `BLENDER_BIN` | discovered | `/Applications/Blender.app/Contents/MacOS/Blender` |

### Graceful Degradation Contract

Every pip-installed and desktop app CLI must implement the same probe/degrade contract used by all existing MCP servers:

1. `probeTimeoutMs: 10000` -- pip CLIs may be slow on first import check
2. `probeTool`: lightest operation (`--version` or import check)
3. On probe failure: log reason, write `status:'unavailable'` to registry, continue workflow
4. `install_hint` in registry entry shown to user in degraded mode output

### Pip CLI vs Binary CLI Classification (discover.cjs logic)

```
Multi-tier classification (zero npm deps, all spawnSync/no shell):

Tier 1: Explicit binary env var  ({TOOL}_BIN)
  -> fs.existsSync(envBin)

Tier 2: PATH lookup
  -> spawnSync('which', [toolName])    (macOS/Linux)
  -> spawnSync('where', [toolName])   (Windows)

Tier 3: pip module check
  -> spawnSync(pythonBin, ['-c', 'import {tool}'])

Tier 4: macOS app bundle via mdfind
  -> spawnSync('mdfind', ['kMDItemCFBundleIdentifier=="{bundleId}"'])
  -> resolve CLI path within .app bundle (e.g., Blender, Sketch's sketchtool)

Tier 5: Well-known install path
  -> hardcoded paths from references/app-integrations.md catalog

Return: { type: 'binary'|'pip-module'|'unavailable', binary, pythonBin, installHint }
```

## Scaling Considerations

This is a local plugin (not multi-user). "Scaling" means handling more wrapped apps without architectural burden.

| Scale | Architecture Adjustments |
|-------|--------------------------|
| 1-5 wrapped apps | registry.json + static TOOL_MAP entries in mcp-bridge suffice |
| 5-20 wrapped apps | `loadDynamicServers()` reads registry.json at module init, populates TOOL_MAP programmatically -- avoids 200-line TOOL_MAP growth |
| 20+ wrapped apps | registry.json is authoritative; TOOL_MAP fully generated from it at load time; Claude Code MCP server slot limit becomes the real constraint |

**First bottleneck:** Claude Code's MCP server slot or tool count limit per session. Mitigate by lazy registration -- only apps with `status:'available'` in registry get added to APPROVED_SERVERS.

**Second bottleneck:** Slow probe times on session init when many apps are registered. Mitigate by caching probe results in `.planning/mcp-connections.json` (already exists and is written by mcp-bridge.cjs) with a 1-hour TTL.

## Anti-Patterns

### Anti-Pattern 1: Hardcoding Every Design App in APPROVED_SERVERS

**What people do:** Add static entries for blender, sketch, figma-cli, affinity, etc. in APPROVED_SERVERS regardless of whether those apps are installed.

**Why it's wrong:** Every stdio server that fails to launch triggers a probe timeout (8-30s each). Ten uninstalled apps = 80-300s of startup hang.

**Do this instead:** `loadDynamicServers()` reads registry.json and only registers apps with `status:'available'`. Discovery runs once per session (cached) and writes status before mcp-bridge reads it.

### Anti-Pattern 2: Installing pip Packages at Plugin Root

**What people do:** Add `requirements.txt` at plugin root and run `pip install -r requirements.txt` during plugin setup.

**Why it's wrong:** Violates the zero-deps-at-plugin-root constraint. Also risks polluting the user's system Python or creating version conflicts. `cad.cjs` already solved this with `CADQUERY_PYTHON`.

**Do this instead:** Each pip CLI gets `~/pde-{tool}-env`. Discovery validates the venv via import check. Plugin ships zero Python.

### Anti-Pattern 3: Invoking App Tools Directly in Workflow Markdown

**What people do:** Embed shell commands like `blender --render-anim scene.blend` directly in wireframe.md steps.

**Why it's wrong:** Bypasses probe/degrade contracts. If Blender is absent, the workflow crashes. Also bypasses TOOL_MAP canonical naming, making the workflow fragile to binary path changes.

**Do this instead:** Always go through `resolveToolName()` -> TOOL_MAP -> generated stdio MCP server. Workflows see only JSON tool calls. Server handles subprocess invocation.

### Anti-Pattern 4: mdfind as the Only Discovery Method

**What people do:** Use `mdfind kMDItemCFBundleIdentifier==...` as the sole app detection strategy.

**Why it's wrong:** Only works on macOS when Spotlight is enabled. Fails on Linux, Windows, or when Spotlight indexing is delayed.

**Do this instead:** Multi-tier probe (Tier 1: env var -> Tier 2: which/where -> Tier 3: mdfind -> Tier 4: well-known paths). First successful tier wins.

### Anti-Pattern 5: Inventing a New TOOL_MAP Naming Convention for App Tools

**What people do:** Use a format like `app__blender__render` instead of `blender:render` -> `mcp__blender__blender_render`.

**Why it's wrong:** Creates a second naming convention that all workflows, probes, and degrade logic must handle specially.

**Do this instead:** App tools follow the identical `{slug}:{capability}` -> `mcp__{slug}__{raw_name}` pattern. The generated MCP server's tool names become the raw names. No special cases.

## Build Order (considering deps on existing infrastructure)

```
Phase A: discover.cjs + references/app-integrations.md
  Deps: child_process (built-in), existing registry.cjs, existing model.cjs
  Delivers: binary resolution for all supported design apps, pip module detection
  Unblocks: Phase B (needs populated registry.json), Phase C (needs discover.cjs)

Phase B: mcp-bridge.cjs loadDynamicServers() + TOOL_MAP generation
  Deps: registry.json format (stable from v0.20), Phase A (writes registry)
  Delivers: dynamic APPROVED_SERVERS + TOOL_MAP at module load time
  Unblocks: Phase E (workflows need TOOL_MAP populated)

Phase C: pde-tools app subcommand
  Deps: discover.cjs (Phase A), mcp-bridge additions (Phase B)
  Delivers: user-facing pde-tools app discover|wrap|register|list|probe
  Parallel: can be developed alongside Phase B

Phase D: server-gen.cjs pip-module handler
  Deps: existing server-gen.cjs, Phase A classification result
  Delivers: correct python -m {tool} spawn pattern in generated MCP servers
  Parallel: can be developed alongside Phase B

Phase E: workflow integrations (wireframe.md, mockup.md)
  Deps: Phases B+C (tools in TOOL_MAP before workflows invoke them)
  Delivers: optional design pipeline steps invoking app tools, with probe/degrade
```

**Critical path:** Phase A -> Phase B -> Phase E. Phases C and D are off the critical path and can be developed in parallel with Phase B.

## Integration Boundaries

### External Services

| Service | Integration Pattern | Notes |
|---------|---------------------|-------|
| Blender | stdio MCP server (generated by server-gen.cjs); binary discovered via PATH/mdfind | `--background` flag required for headless render; server.cjs includes this in args |
| figma-export (npm CLI) | stdio MCP server wrapping npm binary; discovered via PATH | npm global install (`npm install -g figma-export`) -- not pip, no venv needed |
| rembg pip CLI | server.cjs spawns `python -m rembg`; env var `REMBG_PYTHON` | Additive alternative to existing rembg.cjs API client |
| Sketch | stdio MCP server; macOS only; `sketchtool` binary inside Sketch.app bundle | Sketch ships `sketchtool` at `Sketch.app/Contents/Resources/sketchtool/bin/sketchtool` |
| Any `--help` binary | stdio MCP server via help-parser.cjs; universal pattern | No special handling needed |

### Internal Boundaries

| Boundary | Communication | Notes |
|----------|---------------|-------|
| discover.cjs <-> registry.cjs | Direct require(); upsertEntry() call | discover writes status and binary path; registry is append-on-upsert |
| mcp-bridge.cjs <-> registry.json | fs.readFileSync at module load via loadDynamicServers() | No runtime polling; loaded once per session initialization |
| pde-tools app <-> discover.cjs | Direct require() call | Same module boundary as existing cli-anything subcommands |
| workflows <-> mcp-bridge.cjs | require() + resolveToolName() + probeServer() | Identical to how wireframe.md uses Stitch tools today |
