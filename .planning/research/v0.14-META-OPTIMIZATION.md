## 1. Meta-Optimization: Optimizing the Optimizer

### What Meta-Optimization Means in PDE's Context

Meta-optimization is "optimizing the optimizer" -- using an outer optimization loop to improve the parameters of an inner optimization loop. In machine learning, this is hyperparameter optimization (learning rate, batch size, architecture search). In PDE's context, it means:

- **Inner loop:** The standard experiment runner (optimize.md) mutates OPTIMIZABLE prose in a workflow file and measures improvement via a verify command
- **Outer loop:** A meta-experiment mutates the *search space description* in optimize.md itself and measures whether the inner loop converges faster

The PDE instantiation (META-01) is deliberately simple compared to full Bayesian meta-optimization. The outer loop mutates the prose that tells the mutation agent *how* to search, then runs a child experiment to measure whether the guidance produces faster convergence.

**Confidence: HIGH** -- this is a direct application of nested optimization, a well-established pattern.

### How Bayesian Optimization Self-Calibrates (Context for Design Rationale)

Full Bayesian optimization self-calibrates its acquisition function (the function that decides where to sample next) through surrogate model updates. As more evaluations complete, the Gaussian process posterior tightens and the acquisition function naturally shifts from exploration to exploitation. Recent work (Self-Correcting Bayesian Optimization / SCoreBO, NeurIPS 2023) explicitly learns the optimizer location jointly with model hyperparameters.

Dynamic meta-learning acquisition methods (Seifi & Niaki, 2026) start with transfer-based warm-starting and dynamically shift toward data-driven Bayesian modeling as evaluations accumulate. This achieves ~30% better initial performance and ~4% accuracy gain over non-transfer approaches.

**PDE does NOT need this level of sophistication.** The experiment runner operates on prose mutation, not continuous parameter spaces. The simpler "run child experiment, measure improvement rate" approach is appropriate because:

1. PDE's search space is discrete (prose changes), not continuous
2. The eval budget is small (10 outer iterations x 5 inner iterations = 50 total)
3. The cost per evaluation is high (each inner iteration involves an LLM call + screenshot + metric)
4. There is no gradient signal -- improvement is measured by rate, not direction

**Confidence: MEDIUM** -- Bayesian optimization literature is well-established; the claim that PDE doesn't need it is an architectural judgment.

### PDE's META-01 Design: Outer Loop Over Search Space Prose

**Architecture:**

```
OUTER LOOP (meta-experiment, max 10 iterations, 120min total):
  1. Read current optimize.md search space prose
  2. Mutate the search space section (how to approach mutations)
  3. Run INNER LOOP (wireframe-visual experiment, 5 iterations)
  4. Measure: improvement_per_iteration = (final_metric - baseline) / iterations_run
  5. If improvement_per_iteration > best_rate: KEEP mutation; else: DISCARD
  6. Check circuit breakers
END OUTER LOOP
```

**What the outer loop mutates:** Only the `## Search Space` section of the experiment.md template -- the prose that tells the mutation agent what to focus on, what heuristics to apply, and what trade-offs to consider. This is explicitly scoped by META-03: only the search space description is mutable, not orchestrator logic.

**What the inner loop measures:** The wireframe-visual experiment runs against a fixed test concept and measures visual-metric score. The meta-level metric is the *rate* of improvement, not the absolute score -- this tells us whether the search guidance helps the mutation agent converge faster.

**Confidence: HIGH** -- this maps directly to PDE's existing experiment runner architecture; the outer loop is just another experiment that uses a child experiment as its verify command.

### Nested Loop Safety: The Critical Problem

Nested experiment loops are the most dangerous pattern in this milestone. A runaway meta-experiment could:

1. **Resource exhaustion:** Each outer iteration spawns 5 inner iterations, each of which spawns an LLM call + Playwright render + metric evaluation. Worst case: 10 x 5 x (LLM + browser + metric) = 50 expensive evaluations.
2. **Infinite recursion:** If the meta-experiment's verify command spawns another meta-experiment (e.g., due to misconfigured experiment.md path), the system recurses unboundedly.
3. **Git branch pollution:** Each experiment creates an `experiment/{slug}` branch. Nested experiments could create branches-within-branches if not careful.
4. **Convergence to local optima:** The outer loop might find search space prose that converges quickly to a mediocre score, missing better global optima that require slower initial exploration.
5. **Time budget drift:** If the inner loop's 5 iterations take 3 minutes each, each outer iteration takes 15 minutes. 10 outer iterations = 150 minutes, exceeding the 120-minute total budget.

**Confidence: HIGH** -- these are predictable failure modes based on PDE's architecture and general nested optimization risks.

### Prevention Mechanisms (Strict Circuit Breakers)

**Layer 1: Hard Budget Caps (META-02)**

```yaml
# Meta-experiment frontmatter
slug: experiment-calibration
metric: improvement_per_iteration
direction: max
verify: node bin/meta-metric.cjs --child-experiment wireframe-visual --child-iterations 5
mutable_files:
  - workflows/optimize.md
iteration_budget: 10        # HARD CAP: 10 outer iterations maximum
time_budget_minutes: 120    # HARD CAP: 2 hours wall-clock maximum
```

Both caps are enforced by the existing experiment runner circuit breakers (BREAK-01, BREAK-02). No new code needed -- the meta-experiment IS a standard experiment with a special verify command.

**Layer 2: Recursion Depth Guard**

The meta-metric.cjs script MUST check for an environment variable before spawning a child experiment:

```javascript
// bin/meta-metric.cjs
const depth = parseInt(process.env.PDE_EXPERIMENT_DEPTH || '0', 10);
if (depth >= 1) {
  // We are already inside a meta-experiment child -- refuse to go deeper
  process.stderr.write('REFUSE: meta-metric cannot nest beyond depth 1\n');
  process.stdout.write('0\n');
  process.exit(0);  // exit 0 per _evalMetric contract
}

// Set depth for child process
process.env.PDE_EXPERIMENT_DEPTH = String(depth + 1);
// ... run child experiment ...
```

This prevents depth > 1 nesting. The guard is in the metric script, not the orchestrator, so it applies regardless of how the child is invoked.

**Layer 3: Child Experiment Budget Limits**

The child experiment (wireframe-visual with 5 iterations) MUST have:
- `iteration_budget: 5` (not configurable from outer loop)
- `time_budget_minutes: 15` (inner loop timeout per outer iteration)
- Fixed slug prefix: `meta-child-{parent-slug}-{iteration}`

These are hardcoded in meta-metric.cjs, not derived from the outer experiment's configuration.

**Layer 4: Resource Monitoring**

Before each inner loop starts, check:
- Elapsed wall-clock time against the OUTER loop's time_budget_minutes
- If remaining time < inner loop's time_budget_minutes, skip this iteration and halt

```javascript
const outerStartTime = parseInt(process.env.PDE_META_START_TIME || Date.now(), 10);
const outerTimeBudget = parseInt(process.env.PDE_META_TIME_BUDGET || '120', 10) * 60 * 1000;
const elapsed = Date.now() - outerStartTime;
const remaining = outerTimeBudget - elapsed;
const childTimeBudget = 15 * 60 * 1000; // 15 min

if (remaining < childTimeBudget) {
  process.stdout.write('0\n');  // graceful degradation
  process.exit(0);
}
```

**Layer 5: Git Branch Hygiene**

The child experiment MUST:
- Run on a temporary branch that is cleaned up after each outer iteration
- NOT promote changes -- only the outer loop promotes
- Use a distinct branch prefix: `meta-child/` instead of `experiment/`

This prevents branch accumulation across outer iterations.

**Confidence: HIGH** -- these are concrete, implementable safety mechanisms that leverage PDE's existing circuit breaker infrastructure.

### What Can Go Wrong Despite Safeguards

| Failure Mode | Likelihood | Mitigation | Residual Risk |
|---|---|---|---|
| Child experiment hangs (Playwright timeout) | MEDIUM | 15-min child time budget kills it | Brief resource waste |
| Outer loop converges to "always improve in iteration 1, plateau after" | MEDIUM | Rate metric penalizes early-plateau patterns | May miss slow-start strategies |
| Search space prose drifts to nonsensical content | LOW | Boundary violation check on optimize.md LOCKED sections | Mutation agent could write valid but unhelpful prose |
| Git merge conflicts between meta-child branches | LOW | Child branches are ephemeral, never merged to each other | None |
| Token cost exceeds estimate | MEDIUM | 50 inner iterations x ~2000 tokens = ~100K tokens; display at cost gate | User must approve |

## 2. Pipeline Experiments: Cross-Skill Optimization

### The Core Idea

A pipeline experiment changes upstream prose (e.g., brief.md's generation guidance) and measures whether it improves downstream visual output (wireframe screenshot score). This tests the hypothesis: "better upstream guidance produces better downstream artifacts."

**Data flow:**

```
Mutate brief.md OPTIMIZABLE sections
  --> Run brief on fixed test concept (produces BRF-brief-v1.md)
  --> Run system on the brief (produces SYS-tokens-v1.css)
  --> Run wireframe on system+brief (produces WFR-*.html)
  --> Screenshot wireframe HTML via Playwright
  --> Score screenshot via visual-metric.cjs
  --> Return score as pipeline metric
```

**Confidence: MEDIUM** -- the concept is sound but execution complexity is high. Each pipeline run involves 3 LLM calls (brief, system, wireframe) plus screenshot + scoring.

### pipeline-metric.cjs Design

The pipeline metric script orchestrates an abbreviated pipeline run. It is the verify command for PIPE-01 through PIPE-04 experiments.

**Key design decisions:**

1. **Fixed test concept (PIPE-05):** All pipeline experiments use `references/experiments/test-concept.md` -- a canonical product concept brief with known characteristics. This isolates the variable being tested (upstream prose quality) from input variation.

2. **Abbreviated pipeline:** Only run the stages between the mutable file and the final visual output. For brief.md mutations: brief -> system -> wireframe. For system.md mutations: system -> wireframe (skip brief). For flows.md mutations: flows -> wireframe (inject flows into wireframe context).

3. **Temporary workspace:** Pipeline experiments must run in a temporary directory to avoid polluting the user's `.planning/design/` state:

```javascript
const tmpDir = path.join(os.tmpdir(), `pde-pipeline-${slug}-${Date.now()}`);
fs.mkdirSync(tmpDir, { recursive: true });
// Run pipeline stages writing to tmpDir instead of .planning/design/
// Screenshot from tmpDir
// Score from tmpDir
// Clean up tmpDir after scoring
```

4. **Deterministic input:** The test concept must be copied fresh each iteration -- previous pipeline outputs must NOT leak into subsequent runs.

**Confidence: MEDIUM** -- temporary workspace isolation is critical and untested in PDE's current architecture.

### Performance Considerations

| Pipeline Length | Stages | Estimated Time | Feasibility |
|---|---|---|---|
| brief -> system -> wireframe | 3 LLM calls + screenshot + score | 2-5 min | Feasible for 10-20 iteration budget |
| system -> wireframe | 2 LLM calls + screenshot + score | 1-3 min | Good |
| flows -> wireframe | 2 LLM calls + screenshot + score | 1-3 min | Good |
| brief -> system -> flows -> wireframe | 4 LLM calls + screenshot + score | 3-7 min | Marginal -- may exhaust time budget |

**Recommendation:** Pipeline experiments should use `iteration_budget: 10` and `time_budget_minutes: 60` to account for the per-iteration cost. The 3-stage pipeline (brief -> system -> wireframe) at ~4 min/iteration means ~40 minutes for 10 iterations, leaving headroom for the time budget.

### Creating an Abbreviated Pipeline

The pipeline metric script cannot call `/pde:build` (it is a subcommand of the experiment runner, not a user session). Instead, it must:

1. **Direct skill invocation via Task():** The metric script runs inside the experiment runner agent, which can dispatch sub-tasks. But this creates nesting issues.

2. **Better approach: Script-level pipeline.** The metric script runs each stage as a standalone node process:

```javascript
// Simplified pseudocode for pipeline-metric.cjs
const stages = [
  { skill: 'brief', input: testConceptPath, output: `${tmpDir}/brief.md` },
  { skill: 'system', input: `${tmpDir}/brief.md`, output: `${tmpDir}/tokens.css` },
  { skill: 'wireframe', input: `${tmpDir}/brief.md,${tmpDir}/tokens.css`, output: `${tmpDir}/wireframe.html` },
];

for (const stage of stages) {
  // Each stage is a Task() dispatch within the experiment runner
  // This is expensive but correct -- each stage needs LLM reasoning
}

// Screenshot the final wireframe
// Score via visual-metric.cjs
```

3. **Cheapest approach: Pre-compute upstream, only re-run target stage.** If the experiment targets brief.md, pre-compute system and wireframe from the BASELINE brief, then for each iteration only re-run brief + use cached system/wireframe context. This is faster but less accurate -- it doesn't capture how brief changes cascade through the pipeline.

**Recommendation:** Use approach #2 (full abbreviated pipeline) for accuracy. Accept the ~4 min/iteration cost and keep iteration budgets low (10-15). The experiment is measuring cascade effects, so shortcutting the pipeline defeats the purpose.

**Confidence: MEDIUM** -- approach #2 is architecturally correct but performance-dependent on LLM latency and Playwright render time.

## 3. Pressure Test Visual Dimension

### Current State

pressure-test.md runs a full pipeline and evaluates output on two tiers:
- **Tier 1: Process Compliance** -- artifact existence, coverage flags, manifest completeness
- **Tier 2: Design Quality** -- Awwwards rubric text evaluation via pde-pressure-test-evaluator agent

Both tiers are text-based. Adding a visual dimension means rendering the final artifacts in a browser and scoring their visual quality.

### Adding the Visual Dimension (PVIS-01)

After Step 5/7 (Tier 2), add Step 5b: Visual Quality Evaluation:

1. Collect wireframe and mockup HTML files from `.planning/design/`
2. For each HTML file:
   - Navigate Playwright to `file://` (or serve via `npx serve`)
   - Take screenshot
   - Run `bin/visual-metric.cjs` on the screenshot
3. Aggregate scores into a single visual quality score

### Composite Score Formula (PVIS-02)

```
composite = (text_score * 0.6) + (visual_score * 0.4)
```

**Why 60/40 split:**

1. **Text scoring is more reliable.** The Awwwards rubric evaluator has been validated across multiple milestones (v0.4, v0.8, v0.12). Visual metric scripts are new in v0.14 and will have higher variance.

2. **Text captures intent, visual captures execution.** A wireframe can have excellent structural guidance (headings, landmarks, flow) that scores well textually, but render poorly in the browser due to CSS issues. Conversely, a visually polished wireframe might have poor semantic structure. The 60/40 split values intent over execution because PDE generates guidance, not final products.

3. **Alignment with Awwwards judging.** Awwwards itself weights Design (40%), Usability (30%), Creativity (20%), Content (10%). The text rubric already captures all four. Visual scoring adds a "does it actually look right when rendered?" sanity check. It should complement, not dominate.

4. **Calibration path.** Starting at 60/40 allows increasing visual weight in future milestones as confidence in visual metrics grows. A 50/50 starting point would risk penalizing artifacts that score well textually but have rendering artifacts that are noise in the metric.

**Confidence: MEDIUM** -- the 60/40 split is a reasonable starting point but is ultimately a judgment call. Empirical validation during Phase 117 should inform whether to adjust.

### Normalizing Visual Scores to Awwwards 0-10 Scale

The five visual metric scripts produce different ranges:

| Metric | Raw Range | Meaning |
|---|---|---|
| visual-metric | 0-100 (element count + hierarchy depth + landmarks + interactives + whitespace) | Higher = better structure |
| a11y-metric | 0-N violations | Lower = better; unbounded upper |
| contrast-metric | 0-N pass count | Higher = more compliant pairs |
| responsive-metric | 0-100 compliance percentage | Higher = better responsive behavior |
| mermaid-metric | 0-100 readability score | Higher = cleaner diagrams |

**Normalization approach:**

For the pressure test visual dimension, use a min-max normalization with empirically-derived bounds:

```javascript
function normalizeToAwwwards(raw, metric) {
  const bounds = {
    'visual':     { min: 0, max: 80, invert: false },  // typical good wireframe: 40-60
    'a11y':       { min: 0, max: 20, invert: true },    // 0 violations = 10.0; 20+ = 0.0
    'contrast':   { min: 0, max: 15, invert: false },   // 15 text/bg pairs all passing = 10.0
    'responsive': { min: 0, max: 100, invert: false },  // direct percentage
    'mermaid':    { min: 0, max: 100, invert: false },   // direct percentage
  };

  const { min, max, invert } = bounds[metric];
  let normalized = Math.max(0, Math.min(1, (raw - min) / (max - min)));
  if (invert) normalized = 1 - normalized;
  return normalized * 10;  // Scale to 0-10
}
```

The bounds should be calibrated against the Tide test concept baseline during Phase 117 and stored in a config file for future adjustment.

**Confidence: LOW** -- normalization bounds are speculative; must be calibrated empirically with real metric outputs.

### Graceful Degradation (PVIS-03)

When Playwright is unavailable:

```javascript
// In pressure-test visual evaluation step
const playwrightAvailable = await probePlaywright();

if (!playwrightAvailable) {

```

This follows PDE's existing probe/degrade pattern from mcp-bridge.cjs. The pressure test remains functional without browser capabilities -- it just loses the visual dimension.

**Confidence: HIGH** -- probe/degrade is a proven pattern in PDE.

## 4. Ideation Visual Divergence Scoring

### The Problem: Measuring Concept Diversity

When ideation (ideate.md) generates N concepts, we want to measure whether the concepts are actually *diverse* or just variations on a theme. Text-based metrics struggle with this because two concepts can use different words but produce visually identical wireframes.

### The Approach: Screenshot Variance

```
1. Generate N concepts from ideation output
2. For each concept, run wireframe skill -> produce HTML
3. Screenshot each wireframe via Playwright
4. Compute pairwise visual variance across screenshots
5. Higher variance = more diverse ideation
```

### File-Size Standard Deviation as Proxy Metric

**Why file size works as a zero-dependency diversity proxy:**

PNG compression is lossless and content-dependent. The Deflate algorithm (LZ77 + Huffman coding) compresses repeated patterns. Visually different pages produce different spatial frequency distributions, which compress to different sizes.

Research validates this approach:
- PNG file size correlates with human complexity ratings at r=0.24 to r=0.63 depending on image set (imagefluency R package studies)
- The correlation is stronger for structured content (web pages, UI layouts) than for natural photos
- PNG with 90-degree rotation averaging improves correlation, but for wireframe screenshots rotation is unnecessary (they have a fixed orientation)

**For diversity measurement specifically:** We don't need file size to predict complexity -- we need file-size *variance* to detect whether screenshots are similar or different. Two identical screenshots produce the same file size (variance = 0). Two visually distinct screenshots produce different file sizes (variance > 0). This is a weaker but sufficient signal for the diversity question.

**Implementation (zero npm deps):**

```javascript
// bin/divergence-metric.cjs
const fs = require('fs');
const path = require('path');

// Read screenshot file sizes
const sizes = screenshotPaths.map(p => fs.statSync(p).size);

// Standard deviation
const mean = sizes.reduce((a, b) => a + b, 0) / sizes.length;
const variance = sizes.reduce((sum, s) => sum + Math.pow(s - mean, 2), 0) / sizes.length;
const stddev = Math.sqrt(variance);

// Normalize: divide by mean to get coefficient of variation (scale-independent)
const coefficientOfVariation = mean > 0 ? (stddev / mean) * 100 : 0;

process.stdout.write(String(Math.round(coefficientOfVariation * 100) / 100) + '\n');
process.exit(0);
```

**Confidence: MEDIUM** -- file-size SD is a rough but adequate proxy. It will detect gross similarity (3 identical wireframes) and gross diversity (3 very different layouts). It will miss subtle diversity (same layout, different content) and produce false diversity signals (same concept, different screenshot timing artifacts).

### Alternative: Screenshot Hash Uniqueness Ratio

A complementary metric that requires no npm dependencies:

```javascript
const crypto = require('crypto');

const hashes = screenshotPaths.map(p => {
  const buf = fs.readFileSync(p);
  return crypto.createHash('sha256').update(buf).digest('hex');
});

const uniqueHashes = new Set(hashes).size;
const uniquenessRatio = uniqueHashes / hashes.length;  // 1.0 = all unique, 0.33 = all identical

process.stdout.write(String(uniquenessRatio) + '\n');
```

**When to use each:**
- **File-size SD:** Measures degree of visual difference (continuous metric). Better for `direction: max` experiments.
- **Hash uniqueness:** Measures whether screenshots are identical or not (discrete metric). Better as a minimum-bar check (ratio < 1.0 means some concepts produce identical wireframes).

**Recommendation:** Use file-size coefficient of variation as the primary metric for IDIV-01, with hash uniqueness as a secondary diagnostic logged in results.jsonl but not used for keep/discard decisions.

### Minimum Sample Size: 3 Concepts

With 2 concepts, standard deviation is computed from 2 data points -- any difference produces a non-zero SD, and the metric is dominated by single-sample noise. With 3+ concepts, the variance captures genuine distributional properties.

If ideation produces fewer than 3 concepts, the divergence metric should:
1. Log a warning: "Divergence metric requires >= 3 concepts; got {N}"
2. Return 0 (neutral score, no diversity signal)
3. Exit 0 (per _evalMetric contract)

**Confidence: HIGH** -- this is basic statistics (n >= 3 for meaningful variance).

## 5. Brief Reference Capture

### Using Playwright to Screenshot Reference Products

When a brief mentions competitor or reference products with URLs, Playwright can capture screenshots to extract visual patterns.

**Data flow:**

```
1. Parse experiment.md for reference_urls field
2. For each URL:
   a. browser_navigate to URL
   b. browser_take_screenshot (full page)
   c. browser_evaluate to extract patterns:
      - Navigation type (top-bar, sidebar, hamburger)
      - Hero pattern (image, video, text-only, split)
      - CTA density (count of buttons/links above fold)
      - Color scheme (dominant colors from computed styles)
3. Compare extracted patterns against brief.md's analysis guidance
4. Score: what percentage of patterns were correctly identified?
```

### Pattern Extraction via browser_evaluate

```javascript
// Injected into page via browser_evaluate
(() => {
  const nav = document.querySelector('nav, header nav, [role="navigation"]');
  const navType = nav
    ? (nav.querySelector('.hamburger, [aria-label*="menu"]') ? 'hamburger'
       : nav.closest('aside, [class*="sidebar"]') ? 'sidebar'
       : 'top-bar')
    : 'none';

  const hero = document.querySelector('[class*="hero"], main > section:first-child, .banner');
  const heroPattern = hero
    ? (hero.querySelector('video') ? 'video'
       : hero.querySelector('img') ? 'image'
       : 'text-only')
    : 'none';

  const aboveFold = document.querySelectorAll('a[href], button');
  const ctaDensity = Array.from(aboveFold).filter(el => {
    const rect = el.getBoundingClientRect();
    return rect.top < window.innerHeight;
  }).length;

  return { navType, heroPattern, ctaDensity };
})()
```

**Confidence: LOW** -- selector-based pattern extraction is fragile across different sites. Class names vary wildly. This produces useful but noisy signals.

### Security: Opt-In Only (BREF-02)

Brief reference capture MUST be opt-in:

1. **Explicit URL list in experiment.md:** `reference_urls: [url1, url2, ...]` field
2. **No URL discovery:** The metric script never parses brief content for URLs. Only URLs explicitly listed in the experiment frontmatter are accessed.
3. **Domain allowlist:** Only HTTPS URLs are permitted. No HTTP, no file://, no localhost.
4. **User consent at cost gate:** The cost estimate step (Step 4 of optimize.md) should note: "This experiment will access {N} external URLs: {list}"

### Rate Limiting and CAPTCHA Considerations

| Risk | Mitigation |
|---|---|
| Rate limiting by target site | Max 1 request per URL per experiment run; cache screenshots in tmpdir |
| CAPTCHA/bot detection | Playwright runs headless Chromium -- many sites block headless. Use `--headless=new` for new headless mode which is harder to detect |
| Cookie consent banners | browser_evaluate to dismiss common consent banners before screenshot |
| Dynamic loading (SPA) | browser_wait_for text or network idle before screenshot |
| Site unavailable | Timeout after 30s per URL; skip and log; do not CRASH the metric |

**Recommendation:** Brief reference capture should be treated as a "nice to have" experiment -- failures in external URL access should never crash the metric. Return partial scores based on accessible URLs.

**Confidence: MEDIUM** -- the approach is sound but external URL access is inherently unreliable.

### Measuring Brief Guidance Accuracy

The verification question: "Does the brief's competitive analysis guidance correctly identify the visual patterns found in reference sites?"

**Scoring approach:**

```
For each reference URL:
  1. Extract actual patterns via Playwright (navType, heroPattern, ctaDensity)
  2. Run brief.md on a concept that includes this URL as a reference
  3. Parse the generated brief for competitive analysis claims
  4. Compare claims against actual patterns
  5. Score = matching_claims / total_actual_patterns
```

This is the most complex experiment type in v0.14 because it requires:
- External URL access (unreliable)
- Natural language parsing of brief output (fuzzy matching)
- Pattern extraction from arbitrary websites (fragile)

**Recommendation:** Keep this as a stretch goal in Phase 117. If external URL access proves too unreliable, fall back to using locally-served reference HTML pages with known patterns.

**Confidence: LOW** -- high implementation complexity, multiple fragile dependencies.

## 6. Experiment Template Design Patterns

### Standard Template Structure

All experiment templates follow the same YAML frontmatter schema (from templates/experiment.md):

```yaml
slug: {experiment-name}           # Unique identifier, becomes branch name
metric: {metric_name}             # What to measure
direction: max|min                # Higher or lower is better
verify: {shell command}           # Must exit 0, last stdout line = numeric score
mutable_files:                    # Files the mutation agent can modify
  - workflows/{skill}.md
immutable_files: []               # Files to read but not modify (context)
iteration_budget: {N}             # Max iterations before halt
time_budget_minutes: {M}          # Max wall-clock minutes before halt
```

**v0.14 additions for visual experiments:**

```yaml
visual_regression_guard: true|false   # Enable VBRK visual regression circuit breaker
candidates: 1|2|3                     # Multi-candidate mode (MULTI-01)
reference_urls: []                    # For brief reference capture (BREF-02)
```

### Designing Fast Verify Commands (<30s per eval)

**The 30-second target:** Each verify command invocation should complete in <30s to keep experiment iterations responsive. At 20 iterations, that is 10 minutes of pure evaluation time, leaving the remaining budget for mutation agent LLM calls.

**Strategies for fast verification:**

1. **Pre-render, then score:** Separate the rendering step (Playwright navigation + screenshot, ~5-10s) from the scoring step (DOM analysis via browser_evaluate, ~1-2s). If the page is already loaded, scoring is fast.

2. **Reuse browser session:** Don't start/stop Playwright per evaluation. The Playwright MCP server persists across the experiment session. Navigate to the new page and take screenshot -- no cold start.

3. **Limit screenshot resolution:** Use 1280x800 viewport (standard desktop). Full-page screenshots of long wireframes are slow; use viewport-only screenshots.

4. **Batch DOM queries in browser_evaluate:** Instead of 5 separate evaluate calls (headings, landmarks, interactive elements, whitespace, etc.), combine into a single evaluate that returns all metrics:

```javascript
// Single browser_evaluate call returns all visual metrics
const metrics = await page.evaluate(() => ({
  headings: document.querySelectorAll('h1,h2,h3,h4,h5,h6').length,
  landmarks: document.querySelectorAll('[role="main"],[role="nav"],[role="banner"],[role="contentinfo"],main,nav,header,footer,aside').length,
  interactives: document.querySelectorAll('button,a[href],input,select,textarea').length,
  totalElements: document.querySelectorAll('*').length,
  headingHierarchy: checkHeadingHierarchy(),
  whitespaceRatio: computeWhitespaceRatio(),
}));
```

5. **Cache baseline screenshots:** For iterate-delta experiments, the "before" screenshot only needs to be captured once (it is the fixed reference wireframe).

## 7. Safety Summary: Defense in Depth for Nested Experiments

| Layer | Mechanism | Protects Against |
|---|---|---|
| 1. Hard budget caps | iteration_budget: 10, time_budget_minutes: 120 | Runaway outer loop |
| 2. Recursion depth env var | PDE_EXPERIMENT_DEPTH >= 1 -> refuse | Infinite nesting |
| 3. Child budget limits | Hardcoded 5 iter / 15 min per child | Runaway inner loop |
| 4. Wall-clock check before child spawn | Remaining time < child budget -> skip | Time budget overrun |
| 5. Ephemeral child branches | meta-child/ prefix, auto-cleanup | Git pollution |
| 6. Existing circuit breakers | BREAK-01 through BREAK-04 apply to both loops | All standard failure modes |
| 7. LOCKED section markers | optimize.md has LOCKED orchestrator logic | Mutation corrupting experiment runner |
| 8. Boundary validation | experiment-boundaries.md SAFE-04 check | Experiments targeting protected files |
| 9. Model escalation | 3 consecutive violations -> escalate to Sonnet | Persistent boundary violations |
| 10. Cost gate | User approval before meta-experiment starts | Unexpected token cost |
