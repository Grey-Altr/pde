# Stack Research: v0.15 Multi-Editor Integration

**Domain:** Multi-editor MCP server + context generation for AI coding tools
**Researched:** 2026-03-23
**Confidence:** HIGH (MCP SDK, Cursor rules), MEDIUM (Antigravity config, Stitch bridge), LOW (divergence detection tooling)

## Architecture: Dependency Isolation

**Critical constraint:** Zero npm dependencies at plugin root (`/`).

The standalone MCP server lives in an **isolated subdirectory** with its own package.json:

```
pde-mcp-server/           # Separate npm package
  package.json             # Has @modelcontextprotocol/sdk + zod deps
  tsconfig.json
  src/
    index.ts               # #!/usr/bin/env node entry point
    tools/                 # Tool definitions wrapping PDE workflows
  build/                   # Compiled JS output
```

Context generators live in the existing `bin/lib/` as CJS modules — zero new deps.

```
bin/lib/
  context-sync.cjs         # Generates .cursorrules, AGENTS.md, GEMINI.md
  divergence-detector.cjs  # Spec vs code drift detection
  stitch-bridge.cjs        # Antigravity Stitch artifact bridge
```

## Editor Context Format Reference

### Cursor: .cursor/rules/*.mdc (MDC format)

**Confidence:** HIGH — verified from official Cursor docs (cursor.com/docs/context/rules)

```yaml
---
description: "PDE design pipeline context"
globs:
alwaysApply: true
---

# PDE Context
[markdown content here]
```

**Rule types:**
- `alwaysApply: true` — injected into every request (use for project-wide PDE context)
- `alwaysApply: false` with `globs: "*.md"` — auto-attached when matching files in context
- `alwaysApply: false` with `description` only — agent-requested based on relevance
- No frontmatter fields — manually @-mentioned

**Cursor also reads:** AGENTS.md in project root and subdirectories (supported natively).

**PDE generation strategy:** Generate BOTH:
1. `.cursor/rules/pde-context.mdc` with `alwaysApply: true` — full project context
2. `AGENTS.md` in project root — cross-tool foundation (read by Cursor, Antigravity, Gemini CLI)

### Antigravity: AGENTS.md + GEMINI.md

**Confidence:** MEDIUM — verified from antigravity.codes/blog/user-rules and Google AI Developers Forum

**Hierarchy (highest to lowest priority):**
1. `GEMINI.md` — Antigravity/Gemini-specific overrides
2. `AGENTS.md` — Cross-tool shared rules (also read by Cursor, Claude Code)
3. `.agent/rules/` — Additional workspace rule files

**Format:** Plain markdown, no special syntax. Standard sections:

```markdown
# AGENTS.md — [Project Name] Rules

## Tech Stack
## Code Quality
## Testing
## Security
## Git Conventions
```

**Antigravity-specific:** GEMINI.md supports `@file.md` import syntax for modular context.

**Stitch integration:** Antigravity natively connects to Stitch via MCP store. The agent fetches design context and generates a `DESIGN.md` file with extracted colors, typography, and layout rules.

**PDE generation strategy:**
1. `AGENTS.md` — Cross-tool PDE context (same file Cursor reads)
2. `GEMINI.md` — Antigravity/Gemini-specific overrides + `@file.md` imports for modular context
3. Design bridge: PDE handoff artifacts mapped to Antigravity's DESIGN.md convention

### Gemini CLI: GEMINI.md

**Confidence:** HIGH — verified from official Gemini CLI docs (geminicli.com/docs/cli/gemini-md/)

**Hierarchy:**
1. `~/.gemini/GEMINI.md` — Global user-level defaults
2. Project root GEMINI.md — Workspace-scoped (walks parent dirs to .git root)
3. Subdirectory GEMINI.md — Just-in-time context when tools access files
4. Respects `.gitignore` and `.geminiignore`

**Import syntax:** `@./path/to/file.md` — supports relative and absolute paths.

**Configurable filename:** `settings.json` → `context.fileName: ["AGENTS.md", "GEMINI.md"]`

**PDE generation strategy:**
1. `GEMINI.md` in project root — PDE context with `@` imports for modular sections
2. Same file works for both Gemini CLI and Antigravity

## MCP Server Implementation Details

### Package Configuration

```json
{
  "name": "pde-mcp-server",
  "version": "0.15.0",
  "type": "module",
  "bin": {
    "pde-mcp-server": "./build/index.js"
  },
  "dependencies": {
    "@modelcontextprotocol/sdk": "^1.27.1",
    "zod": "^3.25.0"
  },
  "devDependencies": {
    "typescript": "^5.5.0"
  },
  "scripts": {
    "build": "tsc",
    "start": "node build/index.js"
  }
}
```

### Server Entry Point Pattern

```typescript
#!/usr/bin/env node
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { z } from "zod";

const server = new McpServer({
  name: "pde-mcp-server",
  version: "0.15.0",
});

// Register PDE tools (read-only — no write tools per PROJECT.md constraint)
server.tool("pde_get_design_state", "Get current design pipeline state", {
  projectDir: z.string().describe("Path to project root"),
}, async ({ projectDir }) => {
  // Read .planning/DESIGN-STATE.md and return
});

const transport = new StdioServerTransport();
await server.connect(transport);
```

### Client Registration

Editors register the server via their MCP configuration:

**Claude Code:** `claude mcp add --transport stdio pde npx pde-mcp-server`
**Cursor:** Add to `.cursor/mcp.json`
**Antigravity:** Install from MCP store or add to workspace config
**Gemini CLI:** Add to `~/.gemini/settings.json` mcpServers section

### Transport Choice: stdio

Use **stdio** (not HTTP/SSE) because:
- Consistent with PDE's existing Stitch and Playwright MCP patterns (both stdio)
- 12ms average latency vs 45ms for SSE
- No network configuration, no ports, no auth overhead
- npx auto-downloads and runs latest version
- All four target editors support stdio transport natively

## Stitch Design Bridge Architecture

### Problem
PDE already generates Stitch artifacts (STH-*.html/png) via its Stitch MCP integration. Antigravity has its own native Stitch canvas integration. The bridge needs to:
1. Expose PDE's design artifacts in a format Antigravity's Stitch agent can consume
2. Allow Antigravity-generated Stitch designs to flow back into PDE's pipeline

### Solution: File-Based Artifact Bridge (Zero Dependencies)

PDE's stitch-bridge.cjs:
- Reads PDE design-manifest.json for Stitch artifacts
- Generates `DESIGN.md` in Antigravity's expected format (colors, typography, layout from PDE design tokens)
- Reads Antigravity-generated DESIGN.md and maps back to PDE's DTCG token format
- Uses existing `stitch:` TOOL_MAP entries for any live Stitch API calls

No new dependencies — the bridge is a CJS module reading/writing markdown and JSON files.

## Divergence Detection Architecture

### Problem
After PDE handoff, developers implement in their editor. Code drifts from spec.

### Solution: Hash + Structural Comparison (Zero Dependencies)

1. **Handoff snapshot:** SHA-256 hash of handoff TypeScript interfaces stored in `.planning/divergence/baseline.json`
2. **Code scan:** Read actual source files matching handoff component patterns
3. **Structural diff:** Compare exported interface names, prop types, component names
4. **Report:** Generate `.planning/divergence/drift-report.md` with specific deviations

Pattern follows v0.14's visual regression circuit breaker: SHA-256 hash + structural comparison AND-gate.

## Alternatives Considered

| Recommended | Alternative | When to Use Alternative |
|-------------|-------------|-------------------------|
| @modelcontextprotocol/sdk v1.x | SDK v2 (Q1 2026) | When v2 ships stable — migration path is documented. v1.x → v2 is non-breaking for basic server patterns. |
| stdio transport | Streamable HTTP | When PDE server needs to be accessed remotely (future v0.16 Remote Dashboard milestone). |
| Isolated pde-mcp-server/ subdir | npm workspace in plugin root | Never — violates zero-npm-dep constraint at plugin root. |
| Plain CJS context generators | Template engine (Handlebars, EJS) | Never — adds npm dep for simple string interpolation that template literals handle. |
| AGENTS.md as cross-tool base | Separate files per editor | If editors diverge on AGENTS.md support — but as of 2026-03, Cursor, Antigravity, Gemini CLI, and Claude Code all read AGENTS.md. |
| SHA-256 hash drift detection | AST-based comparison (ts-morph) | If hash-based detection produces too many false positives — AST would add a dependency to pde-mcp-server/ subdir. Defer until pain proves it. |

## What NOT to Use

| Avoid | Why | Use Instead |
|-------|-----|-------------|
| Legacy `.cursorrules` file | Deprecated in favor of `.cursor/rules/*.mdc` format. Still works but not recommended for new projects. | `.cursor/rules/pde-context.mdc` + AGENTS.md |
| MCP SDK v2 beta | Not yet stable (anticipated Q1 2026). v1.x is production-recommended. | @modelcontextprotocol/sdk ^1.27.1 |
| HTTP transport for local MCP server | Unnecessary complexity for local tool. Adds auth, CORS, port management overhead. | stdio transport via StdioServerTransport |
| Write tools in PDE MCP server | PROJECT.md explicitly forbids this: "creates second write path bypassing pde-tools.cjs validation and locking" | Read-only tools exposing PDE state; writes go through PDE workflows |
| ts-morph or typescript compiler API | Adds ~15MB dependency for divergence detection that hash comparison handles adequately | crypto.createHash('sha256') + structural JSON comparison |
| npm workspaces | Would make plugin root aware of server subdirectory dependencies | Fully isolated subdirectory with own package.json |

## Integration with Existing MCP Infrastructure

### mcp-bridge.cjs Relationship

The standalone MCP server is a **separate concern** from mcp-bridge.cjs:

- **mcp-bridge.cjs** = PDE consuming external MCP servers (GitHub, Figma, Stitch, etc.)
- **pde-mcp-server** = PDE exposing its own workflows as MCP tools for other editors

No changes to mcp-bridge.cjs needed. The server reads PDE's `.planning/` state files directly.

### TOOL_MAP Expansion

No TOOL_MAP entries needed for the standalone server — it is not consumed via mcp-bridge.cjs. It is consumed directly by external editors (Cursor, Antigravity, Gemini CLI).

### APPROVED_SERVERS

No additions needed — the PDE MCP server is an outbound service, not an inbound integration that needs security gating.
