## Architecture Patterns

### YAML Frontmatter Field Naming Convention

The canonical machine-readable field name for tracking completed requirements in SUMMARY files is:

```yaml
requirements-completed: [REQ-01, REQ-02]
```

Note: hyphen, not underscore. Evidence from 136.1-02 SUMMARY (STATE.md line 79): *"requirements-completed field added to SUMMARY frontmatter separately from requirements_satisfied — both now present, frontmatter field is the canonical machine-readable source"*

The variant `requirements_completed` (underscore, as found in 135-02-SUMMARY.md line 27) is the wrong form and must be corrected.

### Nyquist VALIDATION.md Compliance Pattern

The reference implementation is `136.1-VALIDATION.md` and `136-VALIDATION.md`. A compliant VALIDATION.md has:

**Frontmatter (required fields and values):**
```yaml
---
phase: {phase-number}
slug: {phase-slug}
status: complete          # was: draft
nyquist_compliant: true   # was: false
wave_0_complete: true     # was: false
created: {date}
audited: {date}           # add this field
---
```

**Sign-Off Checklist (all boxes checked):**
```markdown
## Validation Sign-Off

- [x] All tasks have `<automated>` verify or Wave 0 dependencies
- [x] Sampling continuity: no 3 consecutive tasks without automated verify
- [x] Wave 0 covers all MISSING references
- [x] No watch-mode flags
- [x] Feedback latency < 15s
- [x] `nyquist_compliant: true` set in frontmatter

**Approval:** complete
```

**Validation Audit section (add at end):**
```markdown
## Validation Audit {date}

| Metric | Count |
```

## Common Pitfalls

### Pitfall 1: Success Criterion 1 Already Met — Don't Uncheck and Re-check
**What goes wrong:** Planner writes a task that "checks the 136-02 and 136.1-02 checkboxes" without knowing they're already checked, leading to a verify-then-no-op or a redundant edit.
**How to avoid:** The plan task for SC-1 should be "verify checkboxes are already checked" not "check them." If they're already `[x]`, the task is done immediately.

### Pitfall 2: Confusing `requirements_completed` with `requirements-completed`
**What goes wrong:** Editing the wrong field, or adding a duplicate hyphenated field when the underscore form already exists.
**How to avoid:** In 135-02-SUMMARY.md, the edit is a field rename: change `requirements_completed` on line 27 to `requirements-completed`. Do not add a second field — replace the existing one.

### Pitfall 3: 135-VALIDATION.md Wave 0 items reference non-existent files pre-execution
**What goes wrong:** The Wave 0 items say `[ ] dashboard/` which has no file path to check.
**How to avoid:** Rewrite the Wave 0 section with the actual files that were created during Phase 135 execution. Evidence is in 135-01-SUMMARY.md's key-files section (25 files created).

### Pitfall 4: 135-VALIDATION.md references Plan 05 which never existed
**What goes wrong:** Row `135-05-01` in the Per-Task map references a Plan 05. There was no Plan 05.
**How to avoid:** Remove or mark this row as N/A. The 5 DSH requirements were covered by Plans 01-04, not 05.

### Pitfall 5: Sampling continuity check may fail for 135
**What goes wrong:** Plans 135-03 and 135-04 have tasks with no automated verify in the map — they reference `--grep sse` and `--grep session-list` which may not match actual test names.
**How to avoid:** Update the grep patterns to match actual test file names and confirm they produce output. The full suite command `cd dashboard && npm test` covers everything and is the safest fallback.
