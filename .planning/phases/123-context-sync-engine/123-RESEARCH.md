## Summary

Phase 123 adds automatic context file regeneration by wiring a PostToolUse hook into the existing hook infrastructure. When any Write or Edit tool modifies a file under `.planning/`, a new hook script detects the path, checks whether the composite SHA-256 hash has changed, and calls `emitAll()` from `context-sync.cjs` only when state has actually changed. This is the idempotency guarantee required by success criterion 3.

The `/pde:editor-sync` command (CTX-07) is the simpler half of this phase: a new `commands/editor-sync.md` file that delegates to a workflow, which in turn calls `node pde-tools.cjs context-sync` and presents the results to the user. This pattern exactly mirrors how `/pde:check-divergence` delegates to `workflows/check-divergence.md` and calls `divergence.cjs`.

The hook half (CTX-06) is the interesting engineering problem. The existing `emit-event.cjs` already receives `file_path` from PostToolUse payloads, but it does not act on it. A separate new hook script — `hooks/context-sync-hook.cjs` — should be added to `hooks.json` as a second PostToolUse handler that inspects the file path, detects `.planning/` writes, computes the current hash, compares it to the last-written hash stored in a marker file, and runs regeneration only on hash change.

**Primary recommendation:** Add `hooks/context-sync-hook.cjs` as a new PostToolUse hook entry in hooks.json, and add `commands/editor-sync.md` + `workflows/editor-sync.md` following the exact divergence-detection pattern.

### Pattern 1: PostToolUse Hook Script (zero-stdout contract)
**What:** A CJS script that reads hook payload from stdin, inspects file_path, and conditionally runs context regeneration.
**When to use:** Whenever a PostToolUse handler needs to act on file writes.
**Example (from idle-suggestions.cjs — established pattern):**
```javascript
'use strict';
// ZERO STDOUT — all output to /tmp/ only.
const fs = require('fs');
const os = require('os');
const path = require('path');

let raw = '';
process.stdin.setEncoding('utf-8');
process.stdin.on('data', chunk => { raw += chunk; });
process.stdin.on('end', () => {
  try {
    let hookData;
    try { hookData = JSON.parse(raw); } catch { process.exit(0); }

    const filePath = hookData.tool_input && hookData.tool_input.file_path;
    if (!filePath) { process.exit(0); } // not a file write — skip

    // Only act on .planning/ writes
    if (!filePath.includes('/.planning/') && !filePath.includes('\\.planning\\')) {
      process.exit(0);
    }

    // ... hash check + conditional regeneration ...

    process.exit(0);
  } catch { process.exit(0); } // failures must never affect Claude Code execution
});
```

### Pattern 2: Marker-Based Idempotency
**What:** Store last-seen hash in a per-session tmpdir file; only regenerate when hash changes.
**When to use:** Any hook that should fire "at most once per state change" rather than "on every tool call."
```javascript
const markerPath = path.join(os.tmpdir(), `pde-context-sync-${sessionId}.last-hash`);
let lastHash = '';
try { lastHash = fs.readFileSync(markerPath, 'utf-8').trim(); } catch { /* first run */ }

const currentHash = computeSourceHash(planningDir);
if (currentHash === lastHash) { process.exit(0); } // idempotent — no change

// Run regeneration
const { emitAll } = require('../bin/lib/context-sync.cjs');
emitAll(cwd);

// Update marker
fs.writeFileSync(markerPath, currentHash, 'utf-8');
```

### Anti-Patterns to Avoid
- **Writing to stdout in hook scripts:** Claude Code displays hook stdout to the user. All output must go to `/tmp/` files or be suppressed. Every hook must obey the zero-stdout contract.
- **Letting hook failures propagate:** All hook scripts must exit 0 regardless of error. Any exception must be caught and swallowed. Failures must never interrupt Claude Code execution.
- **Calling context-sync.cjs unconditionally on every Write/Edit:** This triggers regeneration even for unrelated files (e.g., writing a source file in src/). The `.planning/` path filter and hash check are both required.
- **Storing state in .planning/ marker files:** The marker tracks per-session idempotency. Storing in .planning/ risks cross-session state pollution. Use `os.tmpdir()` with a session-scoped filename.
- **Modifying emit-event.cjs:** It is the general-purpose event bus. Context-sync logic belongs in a dedicated hook script.

## Common Pitfalls

### Pitfall 1: Bash tool file_path payload gap
**What goes wrong:** The PostToolUse hook for `Bash` does not set `tool_input.file_path` — Bash commands write files as side effects, not as direct tool input. Using `matcher: "Write|Edit|Bash"` means Bash calls reach the hook but always fail the `file_path` check.
**Why it happens:** The `Bash` matcher is used in emit-event.cjs for event logging, not for file path tracking.
**How to avoid:** Use `matcher: "Write|Edit"` (no Bash) for the context-sync hook. Bash-written `.planning/` files will be missed, but the pipeline primarily uses Write/Edit for state files.
**Warning signs:** Hook fires on Bash calls but exits early every time — wasted invocations.

### Pitfall 2: Race condition between async hook and subsequent tool calls
**What goes wrong:** With `async: true`, the hook runs concurrently with the next tool call. If context-sync regeneration is slow, a subsequent read may see stale files.
**Why it happens:** All existing hooks use `async: true` to avoid blocking pipeline execution.
**How to avoid:** Keep `async: true` (do not block). The context files are "best effort" during pipeline execution — they are auxiliary outputs. The SessionEnd or manual `/pde:editor-sync` call provides the definitive regeneration.
**Warning signs:** Context file timestamps lag significantly behind state changes.

### Pitfall 3: Hash computed before .planning/ write completes
**What goes wrong:** PostToolUse fires after the tool completes, but if computeSourceHash is called immediately and the write target is one of the SOURCE_FILES, the new hash should reflect the update. This is fine — PostToolUse fires after the write.
**Why it happens:** Confusion about hook timing — PostToolUse fires AFTER the tool has executed and written.
**How to avoid:** No special handling needed. Hash computation in the hook always sees the just-written file.

### Pitfall 4: Idempotency test — second run produces different timestamps
**What goes wrong:** `generatedAt` in the PDE-GENERATED header is the ISO 8601 timestamp of generation. Running twice with no state change would produce different timestamps, failing the idempotency requirement.
**Why it happens:** `emitAll()` always writes new timestamps.
**How to avoid:** The idempotency requirement is satisfied by the hash gate — the second call never reaches `emitAll()` because the hash has not changed. The success criterion says "running it twice with no state change produces identical output." This is true because the second invocation exits before calling `emitAll()`.
**Warning signs:** If the hash gate is accidentally bypassed, regeneration runs twice and timestamps differ.

### Pitfall 5: cwd resolution in hook context
**What goes wrong:** `process.cwd()` in hook scripts may not equal the project root when spawned by Claude Code.
**Why it happens:** Claude Code spawns hooks from its own working directory.
**How to avoid:** Use `hookData.cwd || process.cwd()` — exactly as idle-suggestions.cjs does. The `cwd` field in the hook payload provides the Claude Code session's working directory.

## Open Questions

1. **Should the hook trigger on SessionEnd as a safety net?**
   - What we know: SessionEnd hook already runs archive-session.cjs. Adding a context-sync call here would guarantee final-state context files at session close.
   - What's unclear: Whether this is needed given async PostToolUse coverage.
   - Recommendation: Add a SessionEnd trigger as a safety net. It is low-cost (deduped by hash gate) and ensures context files are always current when a session ends. This is Claude's discretion — the success criteria do not require it, but it adds robustness.

2. **Should /pde:editor-sync display a diff summary (files changed vs. unchanged)?**
   - What we know: `emitAll()` returns per-emitter results with `written: true/false`.
   - What's unclear: Whether users want diff details or just a confirmation.
   - Recommendation: Display which files were written and the new sourceHash. Simple table output matching the pde-tools.cjs JSON result structure.
